# Decisions Log

Decisions taken autonomously during the build (the operator asked not to be blocked).
Format: decision · options considered · reason.

## D-000 — Work directly on `main`
- **Decision:** Build on `main` instead of `chore/jarvis-setup`.
- **Options:** (a) branch `chore/jarvis-setup` per JARVIS_BUILD_PROMPTS "how to use"; (b) build on `main`.
- **Reason:** That instruction targets adding Jarvis to an existing product repo. This repo *is* the framework repo and had zero commits; a feature branch adds no isolation value and complicates the per-step commit flow requested by the operator.

## D-001 — `dangerouslySetInnerHTML` has a rule ID in two standards files
- **Decision:** Keep both `RX-07` (coding-react.md) and `SEC-10` (security.md); they cross-reference each other.
- **Options:** (a) one rule only; (b) both, cross-referenced.
- **Reason:** The spec lists the rule in both section-12 subsections, and `lint-rules.yaml` in the spec pins the machine-checkable rule to `SEC-10`. A standards reviewer cites `RX-07`, a security reviewer cites `SEC-10`; removing either would break a spec-mandated citation path.

## D-002 — `DB-09` invented to satisfy the DB numbering split
- **Decision:** Added `DB-09 — Bounded context on every query [ADDED]` so MySQL rules fill DB-01..DB-09 and MongoDB starts at the spec-pinned DB-10 (`$lookup`).
- **Options:** (a) leave a numbering gap; (b) add a real rule.
- **Reason:** Gaps in rule IDs look like deleted rules and invite re-use; a genuine MUST rule is more useful than a hole.

## D-003 — `check` reports a missing app directory as `skipped`, not `fail`
- **Decision:** `jarvis.js check` marks a configured command as `skipped` when its working directory (e.g. `apps/api`) does not exist, or when the tool is not installed.
- **Options:** (a) fail; (b) skip with a reason.
- **Reason:** The framework must be installable in a repo before `apps/api` exists, and `doctor` already reports missing tools with install hints. Failing here would make every gate red for reasons unrelated to the work item.

## D-004 — `gates.non_forceable` is matched per finding class, not per phase
- **Decision:** A 3-part key (`review.security.critical`) requires `--accept-risk` only when a recorded issue matches that reviewer *and* severity; a 2-part key (`qa.acceptance_failed`) applies to the whole phase. When a phase has no recorded issues, the entry is treated as hit (fail closed).
- **Options:** (a) any entry whose first segment matches the phase makes the whole phase non-forceable; (b) match the specific finding class.
- **Reason:** (a) would make every review gate non-forceable, which contradicts §8.2 where force is the normal escape hatch and `--accept-risk` is reserved for the listed items.

## D-005 — An unknown finding severity blocks the review gate
- **Decision:** `merge-review` treats a severity outside conventions.md §4 as blocking.
- **Options:** (a) ignore it (it is not in `review.block_on`); (b) fail closed.
- **Reason:** Principle 9, "strict by default". A typo such as `blocker` would otherwise silently let a critical finding through.

## D-018 — Site i18n: two thin parallel route trees, not a `[locale]` + postbuild move
- **Decision:** English lives at the natural unprefixed App Router paths (`app/docs/...`); Thai lives under a real `app/th/docs/...` tree. Each route file is a thin wrapper around shared rendering logic. No postbuild step relocates files.
- **Options:** (a) single `app/[locale]/...` tree with a postbuild script promoting `out/en/**` to `out/**`; (b) two parallel thin trees.
- **Reason:** Next's built-in `i18n` config and middleware do not apply under `output: 'export'`, so locale switching is entirely build-time either way. Option (a) is more DRY but makes `sitemap.xml`, `robots.txt` and the root `404.html` depend on a file-move script getting every edge case right, invisibly, after the build. Option (b) costs ~10 tiny wrapper files (checked for parity by a script) but removes that entire failure class, and GitHub Pages' single global 404 naturally resolves to the true-root English `not-found.tsx` with no extra step.

## D-019 — `/docs/configuration` descriptions are a hand-maintained, drift-checked map

- **Reason:** `yaml.parse` (the same library the CLI uses) does not expose comments as structured data. The generator fails the build if a config key has no description entry, or a description entry refers to a key that no longer exists — so the map can't silently drift from `jarvis.config.yaml`.

## D-022 — Two independent Next.js root layouts, not one shared `app/layout.tsx`
- **Decision:** There is no top-level `app/layout.tsx`. English lives under the route group `app/(en)/layout.tsx` (contributes no URL segment) and Thai under `app/th/layout.tsx` (a real `/th` segment); each renders its own `<html lang="...">`.
- **Options:** (a) one shared `app/layout.tsx` with a hardcoded or client-detected `lang`; (b) two independent root layouts, Next's documented "multiple root layouts" pattern.
- **Reason:** App Router renders exactly one `<html>` per root layout. A single shared layout can't know the locale at the point it renders `<html lang>` without a client-side effect (a hydration-order hack, and wrong for the initial static HTML search engines see). Next explicitly supports parallel root layouts when the top level has no shared layout of its own — each locale gets a correct, static `lang` attribute with no client JS. This refines D-018: the "thin parallel route trees" now start at the layout, not just the page.

## D-025 — Language switch performs a full page navigation (amends D-018/D-022)
- **Finding:** SITE_SPEC.md requires BOTH "English at root with no prefix" AND the language switcher "never causes a full reload." Under Next.js App Router + static export + GitHub Pages (no server, no rewrites), these two requirements are mutually exclusive, and I confirmed this three ways rather than assuming it:
  1. Empirically: a Playwright test set a marker on `window` before clicking the language switch; the marker did not survive navigating from an English page to its Thai counterpart — proof a real document reload occurred, not a client-side transition.
  2. By Next's own documented behavior: "Multiple Root Layouts" (D-022's `(en)`/`th` split, needed for a per-locale static `<html lang>`) explicitly causes a full page load when navigating between them, because the `<html>` element itself is torn down and recreated.
  3. By directly testing the one architecture that could have avoided this — a single shared root layout using an optional catch-all segment (`app/[[...locale]]/...`) so English needs no URL segment at all while still sharing one layout instance. `next build` rejected it outright: "Optional catch-all must be the last part of the URL" — Next forbids nesting any route (e.g. `docs/[...slug]`) beneath an optional catch-all, so this pattern cannot host a real site structure.
- **Options considered:**
  (a) Keep two independent root layouts (correct static `lang`, English unprefixed) — accept the reload.
  (b) A single `[locale]` root layout with English real-routed at `/en` internally, plus a postbuild step that rewrites every internal href from `/en/...` to `/...` and moves the files — technically avoids the reload, but the rewrite must also account for hrefs computed *at runtime, client-side, after hydration* (e.g. the search palette's `router.push`), not just the static HTML — a client-computed link would still say `/en/...` after the promotion, which 404s. This is the exact "silent until deploy" fragility flagged in SITE_PLAN.md §7 risk 2, now confirmed as a real defect mode rather than a hypothetical one.
  (c) Give up the unprefixed-English requirement (always `/en/...`) to get soft navigation.
- **Decision: (a).** A full reload on an infrequent, intentional language switch is a normal, disclosed UX cost (many bilingual static sites behave this way) and does not corrupt state — the destination is still the exact mirrored page, and the choice is still remembered via localStorage. Requirement (c) — clean, permanent URL structure — is materially harder to reverse after launch (bookmarks, backlinks, SEO) than requirement "no reload" is to relax. (b) trades a visible, acceptable cost for an invisible, deploy-time-only one.
- **What changed:** `components/i18n/language-switch.tsx`'s comment now documents the reload instead of claiming there isn't one; `tests/e2e/a11y.spec.ts`'s language-switch test asserts arrival at the correct mirrored URL, not absence of reload.
- **Deviation from SITE_SPEC.md, disclosed:** the switcher does not satisfy "never causes a full reload" under static export on GitHub Pages. Every other clause (keeps the current page, remembers the choice, no prefix for English) is satisfied.

## D-026 — StatusBadge uses a fixed neutral background, not a color-derived tint
- **Decision:** `StatusBadge` renders its icon+label in the indicator color on a fixed `bg-muted` chip, not a `color-mix(in oklch, <indicator color> 12%, transparent)` background.
- **Reason:** A real axe-core pass (not hand-computed math) against the live rendered page found 6 of 15 light-mode indicator colors failing WCAG AA even after two rounds of manual darkening. The root cause was structural: the badge's own background was derived from the same color being tested, so darkening the foreground also darkened its background, partly cancelling the gain. Switching to a fixed neutral background (matching the reference's own badge pattern of colored icon+text on a stable chip) removed the circularity. All 15 tokens were then re-verified against the real computed (color, `--muted`) pair in both themes with a ≥5.0:1 margin, confirmed by a full axe run (0 violations, WCAG 2A+2AA) across 5 pages in both locales and both themes.
- **Process note:** this was caught only because an actual `@axe-core/playwright` run was added in S3 rather than relying on the manual OKLCH math from S2 (D-024) — that math undercounted the real composited background twice before this fix. The e2e a11y suite now runs as part of the site's checks going forward, not as a one-off.

## D-031 — MDX internal links are locale-relative in source; the Anchor component prefixes them
- **Decision:** Every internal link in MDX content is written as `/docs/<slug>` (never `/th/docs/<slug>`), in both English and Thai source files. `components/mdx/mdx-components.tsx` exports `getMdxComponents(locale)` — a factory, not a static object — whose `Anchor` component runs the href through `localizeHref(locale, href)` before rendering.
- **Reason:** Found before it could ship as a real bug: a static component map has no way to know which locale is currently rendering, so a link written in a Thai MDX file would have pointed at the English page unless every translator remembered to hand-prefix every link — an easy, silent mistake with no build-time signal. Making the Anchor locale-aware removes the whole error class; translators (human or subagent) never handle locale prefixing at all.

## D-038 — Fixed two real heading-hierarchy bugs found by Lighthouse's `heading-order` audit, not by axe

## D-042 — GitHub Actions deploy workflow: `release: published`, not tag-glob matching, for release deploys
- **Decision:** `.github/workflows/site.yml` triggers on `push` to `main` (path-filtered to `site/**`, `.claude/**`, `.jarvis/**`, `CHANGELOG.md`) and separately on `release: types: [published]`, plus `workflow_dispatch` for manual re-runs.
- **Reason:** The S8 prompt asks for "on push to main (paths: …) and on release tags." A single `push` trigger with both `branches`/`tags` filters and a `paths` filter applies the `paths` filter to every matching ref including tags — a release tag pointing at a commit that only touched, say, `jarvis-framework/bin/`, would then silently skip deploying the site even though a real release just shipped. Using the separate top-level `release: types: [published]` event avoids this entanglement entirely (releases always deploy, regardless of which paths their commit touched) and is also the more idiomatic GitHub Actions trigger for "deploy when a release goes out" than matching a tag name pattern.
- **Two more real gotchas fixed in the same workflow, not assumed:** (1) `check:links` runs *after* `npm run build`, not literally between "i18n check" and "build" as the prompt's step list reads — the checker validates the real static `out/` directory's rendered anchors, which don't exist until after `next build`. (2) added `touch out/.nojekyll` before the Pages upload step — GitHub Pages' default Jekyll processing silently drops any path starting with `_`, which would 404 every asset under Next's `_next/` directory on first deploy if omitted; this is a known, easy-to-miss Next.js-on-GitHub-Pages failure mode, not a hypothetical one.
- **Configurability:** `SITE_BASE_PATH` and an optional `SITE_CNAME` are read as GitHub Actions repository variables (`vars.*`), not hardcoded — a project-page deploy sets `SITE_BASE_PATH=/jarvis-framework`; a custom-domain or user/org-page deploy leaves both adjusted per `site/README.md`'s Deployment section.

## D-044 — `SITE_BASE_PATH` must be a job-level env, not just on the `build` step
- **Finding:** The second real deploy run passed `npm run build` but failed `npm run check:links` with 35 broken links, all involving the `/jarvis-framework` basePath prefix (e.g. `docs/agents/index.html -> /jarvis-framework/docs/gates/`). ## D-049 — Agent coverage expansion: DevOps and Lead/Staff as agents, PM as a CLI command
- **Audit finding:** of the roles a real SDLC team has, 15 were already covered by the 17 agents (BA ×2, PO, SA, UX, planner, backend, frontend, QE ×2, security, DBA, perf, release, gatekeeper, investigator). Full-stack is covered by decomposition, not by an agent: `plan.md` assigns each task a `layer`, and the orchestrator routes backend and frontend tasks to different agents, so one person's full-stack work becomes two single-layer tasks. - **Engine change this required:** phases gained `conditional_agents: { <flag>: [agent] }`, resolved by `agentsFor(phase, flags)` and surfaced as `agents_resolved` from `jarvis.js next`. - **PM → a CLI command, not an agent.** `jarvis.js portfolio` plus `jarvis.js link <ID> --depends-on <ID>`, surfaced as `/jarvis-portfolio`.

Judgement (what to prioritise, which conflict matters) still belongs to a model, so the slash command hands the JSON to Claude to summarize and rank; the numbers come from the CLI, the ordering from the model.

- **Lead/Staff → `jarvis-staff`, deliberately outside the workflow.** It has no phase, no work item and no gate — it is the only agent like that. `jarvis-review-standards` judges one diff against the rules; nothing asked whether the system as a whole had drifted from its own ADRs, or whether it was getting harder to change.   - **When it runs:** on demand via `/jarvis-health`; when the newest report exceeds `staff_review.max_age_days` (new config key, default 30), which `jarvis.js health` reports and `status --brief` warns about; and before a minor or major release, via release checklist item `REL-13`.

  - **Staleness is not nagged on a fresh repo:** `status --brief` warns only when a report exists and has aged out. A repo that has never run one is reported by `jarvis.js health` but does not warn on every status line.

## D-050 — The 24 "pre-existing" e2e failures were a stray `next dev` server, not a code regression
- **Symptom:** 24 of 90 Playwright tests failed — the axe `scrollable-region-focusable` violation on `/docs/workflows` in both locales, and a cluster of JS-interaction timeouts (clipboard toast, ⌘K palette, mobile nav sheet, pipeline keyboard nav). Identical failure sets before and after D-049, so not caused by that work. D-047/D-048 recorded 90/90 green.
- **Ruled out first:** `site/package-lock.json` has not changed since step S6 — long before D-047/D-048 — and installed versions match it exactly (Playwright 1.63.0, Next 16.3.5, axe-core 4.13.0). No dependency drift, so the "versions moved under us" explanation was wrong.
- **Root cause:** `playwright.config.ts` served the built export with `npx serve out -l 3000` under `reuseExistingServer: !process.env.CI`. A `next dev` process (PID 46534, started 09:00 that morning) was still listening on port 3000, so Playwright reused it and **tested the dev server instead of the static export**. Confirmed directly: the page under test loaded `ws://127.0.0.1:3000/_next/hmr`, a string that appears nowhere in `out/`; `curl` showed the dev server 308-redirecting `/docs/workflows` to a trailing slash where the export serves it directly.
- **Why that produced exactly those failures:** every failing test needed hydration to have completed. A dev server compiles the route on demand, so at assertion time the page was still pre-hydration — clicks did nothing, and Radix's roving `tabindex` had not been applied, leaving the horizontally scrollable phase row with no focusable descendant for axe to find. The passing 66 were all static-render assertions, which do not care.
- **The axe violation was not a real accessibility bug.** Verified against the shipped artifact rather than assumed: `out/docs/workflows/index.html` already contains `<button role="tab">` with a default (focusable) tabindex inside the `md:overflow-x-auto` container, server-rendered, before any JavaScript runs. A real user never sees the state axe was complaining about — only a test pointed at a mid-compile dev server does.
- **Fix:** the e2e server moved to a dedicated port 4321 with `reuseExistingServer: false`, so the suite always starts its own server against the built `out/` — the artifact that actually ships to GitHub Pages — and can never silently grade a different build. Port 3000 is left to `next dev`.
- **Verified:** 90/90 on three consecutive runs **with the stray dev server still running**, which is the proof this is a fix and not a retry-until-green. Run time dropped from 1.3m to ~13s, because the suite no longer waits on on-demand compilation.
- **Contributing weakness, not fixed here:** `.github/workflows/site.yml` never runs Playwright — only typecheck, lint, build and `check:links`. The e2e suite is local-only, so the `reuseExistingServer` condition was effectively always true in practice, and nothing outside a developer's machine would ever have caught this. Adding e2e to CI (with a browser install step) would close that gap; it is a real cost/benefit call on CI minutes, so it is recorded here rather than decided unilaterally.
- **Process note:** the same lesson as D-043/D-044 in a new form — the failure was invisible to reading the code, and only a real run, interrogated rather than retried, surfaced it. "Pre-existing on main" is a reason to investigate, not a reason to accept.

- **Decision:** `.github/workflows/site.yml` runs `npx playwright test` after `check:links`, against the same `out/` that is about to deploy. Chromium only, cached under `~/.cache/ms-playwright`, with the HTML report uploaded as an artifact on failure.
- **Options:** (a) keep it local-only and document that; (b) run it in CI.
- **Reason for (b):** typecheck, lint and `check:links` all pass on a page whose JavaScript never runs — the e2e suite is the only check in the repo that covers hydration, keyboard operation and axe accessibility. D-050 is the argument in full: a stray `next dev` server made every local run grade the wrong build for an unknown period, and because nothing ran the suite anywhere else, there was no second opinion to catch it. A suite that only ever runs on one machine is one that can be silently invalidated, or simply skipped before a push.
- **Cost, measured not guessed:** 90 tests across the light and dark projects in ~13s against the static export, plus a Chromium download that the cache removes on later runs.
- **It runs as its own `e2e` job, in parallel with `build`, and `deploy` needs both.** The first attempt put the steps in the `build` job and failed on CI with 52 of 90 red — every axe test on every page, not the local picture at all. Cause: `build` sets `SITE_BASE_PATH: /jarvis-framework` job-wide (D-044), so the export lives under that prefix while the specs navigate to `/docs/...`; the page served at `/` was not the page, and `<html lang>` came back `null`. Reproduced locally with `SITE_BASE_PATH=/jarvis-framework npm run build` before changing anything — 33 of 45 in the light project, matching CI.
- **Fixed by building without a basePath in the e2e job rather than teaching the specs about the prefix.** The behaviour under test — hydration, keyboard operation, axe — does not depend on the deploy basePath, and `page.goto("/docs/x")` is an absolute path that discards a `baseURL` path component, so a prefix-aware `baseURL` would not have worked without rewriting every `goto` in three spec files. The basePath-prefixed link graph of the real deploy artifact is already covered by `check:links` in the `build` job, which is the tool that exists for exactly that. Verified both directions locally: with the prefix 33/45, without it 90/90.
- **`--with-deps` runs even on a cache hit:** the cache holds the browser, not the apt libraries it links against; the command skips the download when the browser is already present.
- **Avoided:** the `${{ cond && 'a' || 'b' }}` ternary, which in GitHub Actions falls through to the right-hand side whenever the left is an empty string, so a cache hit would still have taken the `--with-deps` branch. A plain unconditional step is correct here and does not need the trick.
- **Reporter is conditional:** `list` locally, `list` + `html` on CI. A runner has no terminal to scroll back through, and the trace and screenshot live in the HTML report.

### G5 scans a command's arguments, not the data it carries
- **Symptom:** `cat >> DECISIONS.md <<'EOF' … EOF` was blocked as a secret read because the heredoc body — the D-050 text — contained `process.env.CI`. The old pattern ran `.env\b` across the whole command string, so any prose after a read command matched.
- **Two faults, both fixed:**
  1. **Data was scanned as arguments.** `stripCommandData` now removes heredoc bodies (terminated or not) before matching. Quoted strings are handled by a rule that keeps real paths: a quoted token *without* whitespace stays (`cat '.env'` is still a read), one *with* whitespace is dropped as prose (`git commit -m "fix process.env.CI"` is not). Quoting a path is therefore not a bypass.
  2. **`.env` matched mid-identifier.** The pattern is now anchored with a negative lookbehind, `(?<![\w.])\.env`, mirroring `SECRET_FILES`' own `(^|\/)\.env(\.|$)`. `process.env.CI` and `import.meta.env` no longer match; `.env`, `.env.local`, `./.env` and `apps/api/.env` still do.
- **Known limit, accepted and commented in the source:** a secret filename containing a space (`cat 'my secrets.env'`) is dropped by the quoted-token rule. The file-path branch of G5 and the `Read` deny-list in `.claude/settings.json` still cover it, and the alternative — treating every quoted string as a path — reinstates the false positive this fixes.
- **Verified:** three new tests in `guard.test.js` — every spelling of a real secret read still blocks (bare, quoted, `./`-prefixed, nested path, `source`, `cp`, `id_rsa`, `.pem`, `credentials.json`); heredoc bodies and quoted prose are allowed, including the exact command that was blocked; and a quoted secret path still blocks, so the new rule is not an escape hatch. 75/75 script tests pass, audit 9/9.
