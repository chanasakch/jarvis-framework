# Jarvis Framework — Build Specification v1.0

> Source of truth for building the Jarvis framework on Claude Code.
> Claude Code must read this file before creating or changing any framework file.
> All framework files and all generated artifacts are written in **English** (token efficiency).

---

## 0. Purpose

Jarvis is an AI-driven SDLC framework running on Claude Code. It routes work to specialist subagents,
validates every output against team standards (script gate + gatekeeper agent + human approval),
and blocks progress until each phase meets its Definition of Done.

Target project:
- Monorepo
- Frontend: React + TypeScript
- Backend: Go
- Databases: MySQL and MongoDB
- Cache: Redis (configurable)
- Usage: solo now, team later → every design decision must be team-ready.

---

## 1. Design Principles

1. **Orchestrator = slash command** running in the main session. Subagents cannot spawn subagents, so all delegation happens from `/jarvis`.
2. **File-based handoff.** Agents exchange file paths, never pasted content.
3. **Three-layer gates:** deterministic script → gatekeeper agent → human approval (configured phases).
4. **Hooks enforce hard rules.** Anything that must never happen is blocked by `guard.js`, not by prompt text.
5. **Traceability IDs** link every artifact: FR → US → AC → TC → code → release.
6. **Configuration over code.** Workflows, gates, commands and thresholds live in YAML.
7. **Framework-owned vs project-owned files** are separated so upgrades never overwrite team standards.
8. **Every exception to a standard requires an ADR.**
9. **Strict by default.** Force is possible but explicit, human-only, warned and audited.
10. **Token discipline.** Short English artifacts, agents load only the standards they need.

## 4. Work Types and Workflows

### 4.1 Work types

| Type | ID prefix | Use when |
|---|---|---|
| feature | FEAT | New capability |
| enhancement | ENH | Change to existing capability |
| bugfix | BUG | Defect found before/after release, not urgent |
| hotfix | HOT | Production incident, urgent |
| refactor | REF | Internal change, no behavior change |
| performance | PERF | Measurable speed/resource improvement |
| security | SEC | Vulnerability fix or security hardening |
| migration | MIG | Schema/data migration (MySQL or MongoDB) |
| spike | SPK | Time-boxed research, no production code |
| chore | CHR | Dependency upgrade, config, CI, tooling, docs |

### 4.2 Phase sequences

`(A)` = human approval by default · `(opt:flag)` = skipped when flag is false · `mode` = agent mode

| Type | Phases |
|---|---|
| feature | intake → brief → requirements(A) → business-flow → ux(opt:has_ui, A) → architecture(A) → plan → implement → test → review → qa → release(A) |
| enhancement | intake → requirements(A, mode: delta) → business-flow(opt:changes_flow) → ux(opt:has_ui, A) → architecture(A, mode: lite) → plan → implement → test → review → qa → release(A) |
| bugfix | intake → investigation(mode: bug) → plan → implement → test(mode: regression) → review → qa → release(A) |
| hotfix | intake → investigation(mode: hotfix) → implement → test(mode: regression) → review(security + standards blocking; others advisory) → release(A) → postmortem(deferrable ≤ 3 days) |
| refactor | intake → investigation(mode: refactor) → architecture(A, mode: lite) → plan → implement → test(mode: parity) → review → qa(mode: parity) → release |
| performance | intake → investigation(mode: baseline) → architecture(A, mode: lite) → plan → implement → test(mode: benchmark) → review → qa → release |
| security | intake → investigation(mode: threat) → architecture(opt:design_change, A) → plan → implement → test(mode: exploit) → review → qa → release(A) |
| migration | intake → requirements(A, mode: lite) → architecture(A, mode: migration) → plan → implement → test(mode: migration) → review(database blocking) → qa → release(A, runbook mandatory) |
| spike | intake → investigation(mode: spike) → end (outputs spike-report + ADR draft; may create follow-up items) |
| chore | intake → plan(mode: lite) → implement → test → review → release |

### 4.3 Intake flags

Set during intake (orchestrator asks the user, max 5 questions, batched):
`has_ui`, `has_api_change`, `has_db_change`, `has_mysql`, `has_mongo`, `changes_flow`, `design_change`, `touches_auth`, `touches_pii`, `has_infra_change`.

`has_infra_change` is true when the item touches CI/CD workflows, infrastructure-as-code, Dockerfiles,
k8s/Helm manifests, or deploy, monitoring or alerting config. It gates `jarvis-devops` into the
architecture and release phases and `jarvis-review-devops` into review.

### 4.4 Workflow YAML schema (`.jarvis/core/workflows/<type>.yaml`)

```yaml
name: feature
id_prefix: FEAT
phases:
  - id: intake
    owner: orchestrator
    outputs: [intake.md]
    template: [intake.md]
    checklist: intake.md
  - id: requirements
    agent: jarvis-po
    mode: full
    requires: [brief]
    inputs: [brief.md]
    outputs: [prd.md, stories.md]
    template: [prd.md, user-story.md]
    checklist: requirements.md
    standards: [documentation.md]
    approval: human
  - id: ux
    agent: jarvis-ux
    optional_if_false: has_ui
    requires: [requirements, business-flow]
    approval: human
  - id: implement
    agents: { backend: jarvis-dev-backend, frontend: jarvis-dev-frontend }
    loop: per_task
    deterministic_checks: [backend.format, backend.lint, backend.test, frontend.lint, frontend.typecheck, frontend.test, jarvis_lint]
  - id: review
    agents: [jarvis-review-standards, jarvis-review-performance, jarvis-review-security, jarvis-review-database]
    conditional_agents:            # appended only when the flag is true
      has_infra_change: [jarvis-review-devops]
    conditional_outputs:
      has_infra_change: [review/devops.md]
    parallel: true
    blocking_reviewers: all        # or list, e.g. [security, standards] for hotfix
    on_fail: implement
    reviewer_standards:
      devops: [devops.md, security.md, logging.md]
```

`approval` defaults come from `gates.human_approval`; a workflow may override per phase.

`conditional_agents: { <flag>: [agent, ...] }` appends an agent to a phase only when that intake flag
is true. `jarvis.js next` resolves it and returns the result as `agents_resolved`, which is what the
orchestrator delegates to; `validate` and `merge-review` use the same resolution, so a conditional
reviewer is never demanded on an item where it did not run.

## 6. Conventions (content of `.jarvis/core/rules/conventions.md`)

### 6.1 IDs
- Work item: `<PREFIX>-<NNN>` (e.g. `FEAT-012`), sequential per prefix.
- Scoped to a work item: `FR-001`, `NFR-001`, `US-001`, `AC-001-01` (story 001, criterion 01), `BR-001`, `UX-001` (screen), `T-001`, `TC-001`, `F-<REVIEWER>-001` (review finding, e.g. `F-SEC-001`), `D-001` (defect), `R-001` (risk), `Q-001` (open question).
- Repo-wide: `ADR-0001`.
- Standards rules: `<AREA>-NN` (e.g. `GO-03`, `DB-01`, `SEC-07`).
- Cross-reference format in text: `[US-003]`.

### 6.2 Artifact front matter (every artifact)
```yaml
---
id: FEAT-012
artifact: prd
version: 1
status: draft          # draft | final
refs: [brief.md]
---
```

### 6.3 Phase statuses
`pending` · `in_progress` · `gate_failed` · `passed` · `approved` · `forced` · `skipped` · `blocked` · `parked`
A phase unlocks the next when it is `approved` (approval required), `passed` (no approval required), `forced`, or `skipped` (optional phase only).

### 6.4 Severity
- **critical** — security vulnerability; data loss/corruption; acceptance criterion not met; internal error details returned to the client; external input without validation or sanitization.
- **major** — violation of any MUST rule in standards; SQL JOIN or Mongo `$lookup` without ADR; query not covered by an index; query/HTTP/cache call inside a loop (N+1); O(n²) or worse on unbounded input where a better approach exists; missing log at an error boundary; error not in registry; AC without test.
- **minor** — SHOULD violations, naming, readability, small duplication.
- **info** — suggestions.

### 6.5 Writing rules for artifacts
English only · no filler or restating the template · tables over prose · Mermaid for all diagrams · no `TBD`/`TODO`/`???` in final artifacts (use `Q-xxx` open questions instead).

## 8. Gate Protocol

1. Agent returns `status: DONE`.
2. **Script gate:** `jarvis.js validate <ID> <phase> --json` (structure, IDs, traceability, deterministic checks, lint rules).
3. Script FAIL → send issues back to the same agent; `attempts++`.
4. **Agent gate:** invoke `jarvis-gatekeeper` with artifact, checklist, upstream artifacts.
5. Gatekeeper FAIL → send issues back to the same agent; `attempts++`.
6. `attempts == gates.max_retries` → STOP and print the **Gate Failure Menu**.
7. PASS → `jarvis.js set <ID> <phase> passed`. If approval is required → STOP and print approval instructions. Otherwise continue to the next phase.

### 8.1 Gate Failure Menu (orchestrator prints exactly this shape)
```
⚠️  GATE FAILED: FEAT-012 / review (attempt 3/3)
Blocking issues:
  - [F-SEC-001][critical] Raw DB error returned in POST /v1/otp response
  - [F-PERF-002][major] Query inside loop in otp/service.go:88
Risk if forced: <one or two lines>
Options:
  1) Retry — send issues back to the agent (resets attempts)
  2) Fix manually, then run: /jarvis FEAT-012
  3) Force pass (human only, audited):
     ! npm run -s jarvis -- force FEAT-012 review --reason "<why>"
  4) Park work item:
     ! npm run -s jarvis -- park FEAT-012 --reason "<why>"
```
The user may ask to force at any time; the orchestrator prints the same menu with current issues.

### 8.2 Force rules
- CLI only; `guard.js` blocks Claude from running human-only commands.
- `--reason` mandatory. Items in `gates.non_forceable` also require `--accept-risk`.
- Records `forced_by` (git `user.name`), time, reason, unresolved issue IDs.
- Auto-creates a follow-up `CHR` work item listing unresolved issues.
- Forced gates appear in a **Forced Gates** section of qa-report.md and release-notes.md.
- Orchestrator shows `⚠️ <ID> has N forced gate(s): <phases>` at every later step for that item.

### 8.3 Approve, skip, reopen, park
- `approve <ID> <phase>` — human only; phase must be `passed`.
- `skip <ID> <phase> --reason` — human only; only phases marked optional.
- `reopen <ID> <phase>` — human only; resets that phase and all downstream phases to `pending`.
- `park` / `unpark` — human only.

## 9. Orchestration Protocol (content of `.jarvis/core/rules/orchestration.md`, used by `/jarvis`)

Input: new request text, a work item ID, or empty (resume most recently active item).

1. Load: `jarvis.config.yaml`, `conventions.md`, status summary (`jarvis.js status --json`).
2. **New request → intake** (the only phase the orchestrator performs itself):
   - Propose work type with one-line justification; confirm with user.
   - Ask flag questions (max 5, numbered, one message).
   - `jarvis.js new <type> "<title>" --flags ...` → write `intake.md` from template → gate it.
3. `jarvis.js next <ID> --json` → returns `{action, phase, agent(s), mode, inputs, outputs, templates, checklist, standards, approval}`.
   - `action: awaiting_approval` → print approval command and stop.
   - `action: done` → print summary and stop.
4. `jarvis.js set <ID> <phase> in_progress`.
5. Delegate via Task tool with a **Handoff Brief** (9.1).
6. On `BLOCKED` with open questions → ask user (numbered, one message) → resend Handoff Brief with `user_answers`.
7. On `DONE` → Gate Protocol (section 8).
8. **Implement phase:** read tasks from plan.md in dependency order; one task per subagent call; route by task `layer` (backend/frontend); after each task run `jarvis.js check <layer>` and `jarvis.js lint --changed`; mark task via `jarvis.js task <ID> <T-xxx> done`. Gate the phase after all tasks.
9. **Review phase:** invoke all enabled reviewers **in parallel** (multiple Task calls in one message). Each writes `review/<reviewer>.md`. Then `jarvis.js merge-review <ID>` creates review-report.md and verdict. Blocking findings → set phase back to implement with findings as fix tasks (`FIX-<finding-id>`).
10. Continue automatically to the next phase until approval, failure menu, question, or done.
11. End every turn with the **Status Report** (9.2).

Hard rules for the orchestrator: never do phase work itself (except intake); never edit `.jarvis/state` directly; never run human-only CLI commands; never paste artifact contents into handoffs; summarize agent results in ≤ 5 lines.

### 9.1 Handoff Brief format
```
HANDOFF
work_item: FEAT-012 (feature) "OTP login"
phase: architecture | mode: full
flags: has_ui=true has_db_change=true has_mysql=true has_mongo=false
read:
  - docs/work/FEAT-012-otp-login/prd.md
  - docs/work/FEAT-012-otp-login/stories.md
  - .jarvis/project/context.md
standards: [.jarvis/standards/api.md, .jarvis/standards/database.md]
template: .jarvis/core/templates/tech-spec.md
checklist: .jarvis/core/checklists/architecture.md
write:
  - docs/work/FEAT-012-otp-login/tech-spec.md
task: (implement only) T-003
previous_gate_issues: none | [list]
user_answers: none | [list]
```

### 9.2 Status Report format
```
── JARVIS ─────────────────────────────
Item:   FEAT-012 OTP login (feature)
Phase:  architecture → passed (attempt 1) ✅
Waiting: human approval
Next:   ! npm run -s jarvis -- approve FEAT-012 architecture
Warnings: none
───────────────────────────────────────
```

## 10. Agents

### 10.1 Common file structure (every `.claude/agents/jarvis-*.md`)
```markdown
---
name: jarvis-<role>
description: <when to use; orchestrator routes on this>
tools: <minimal set>
model: <from config>
---
# Role
# Modes            (if any)
# Inputs           (always from Handoff Brief)
# Outputs
# Process
# Must
# Must Not
# Self-Check       (run checklist before returning)
# Return Format
```

### 10.2 Return format (all agents)
```
RESULT
status: DONE | BLOCKED
artifacts: [paths]
summary: <≤5 lines>
open_questions: [Q-001: ...] | none
self_check: pass | [failed item IDs]
```
Subagents cannot talk to the user; questions go through `open_questions`.

### 10.3 Agent specifications

**jarvis-gatekeeper** — tools: Read, Grep, Glob. Judges one phase's artifacts against its checklist and upstream artifacts. Verifies every Blocking item with evidence (line or ID); verifies referenced IDs exist upstream and that upstream items are fully covered. Never edits files; never passes "almost complete". Returns:
```json
{"verdict":"PASS|FAIL","blocking":[{"item":"REQ-03","evidence":"US-004 has no AC","fix":"Add Given/When/Then AC"}],"advisory":[]}
```

**jarvis-analyst** — tools: Read, Write, Glob, Grep. Writes brief.md. Separates problem from solution; quantifies goals (metric + target); lists stakeholders, assumptions, constraints, impacted systems (scan repo); no solution design.

**jarvis-po** — tools: Read, Write, Glob, Grep. Modes: full, delta, lite. Writes prd.md and stories.md.
Must: FR/NFR IDs with MoSCoW; stories follow INVEST; each story has AC in Given/When/Then including negative, validation and error cases; error cases reference user-facing outcomes (public message keys), never internal detail; NFRs cover performance budget, security, logging/audit, data retention, availability; explicit Out of Scope. Delta mode marks items `[NEW] [CHANGED] [REMOVED]` against the existing behavior.

**jarvis-ba** — tools: Read, Write, Glob, Grep. Writes business-flow.md: to-be flowchart (and as-is for enhancement), sequence diagram per key story, state diagram for entities with lifecycle, business rules `BR-xxx` each traced to FR/US, edge-case table. Mermaid only.

**jarvis-ux** — tools: Read, Write, Glob, Grep. Writes ux-spec.md for React: screens `UX-xxx`, component tree reusing `packages/ui` (scan first), states (loading/empty/error/success/disabled), field validation rules mapped to AC, error display via public message keys only, accessibility (WCAG 2.1 AA), responsive breakpoints. No code.

**jarvis-investigator** — tools: Read, Write, Glob, Grep, Bash (read-only: git log/blame/show, go test -run, explain queries). Modes:
- bug/hotfix: reproduction steps, expected vs actual, root cause with evidence (file:line, logs), 5-whys, impact, fix options.
- refactor: current behavior inventory, scope, risks, parity criteria.
- baseline (performance): measurement method, baseline numbers (pprof, MySQL EXPLAIN, Mongo explain, React Profiler), bottlenecks, target.
- threat (security): vulnerability description, severity (CVSS-style), attack vector, affected assets, containment.
- spike: questions, time-box, options compared, recommendation, ADR draft.
- postmortem: blameless timeline, impact, root cause, action items as follow-up work items.
Never modifies source code.

**jarvis-architect** — tools: Read, Write, Glob, Grep. Modes: full, lite, migration. Must read `.jarvis/project/context.md` and relevant code first. tech-spec.md must include:
- C4 context/container + sequence diagrams (Mermaid)
- FR → component mapping (every FR)
- Layering per `structure.md`
- API contract delta as OpenAPI 3 (`api-contract.yaml`)
- **Data design without JOIN / $lookup:** denormalization or reference IDs + batched lookups, documented per read path
- **Query-Index Matrix:** every read/write path → query shape → supporting index (MySQL and MongoDB, ESR rule for Mongo)
- **Cache design:** keys, TTL + jitter, invalidation, stampede protection
- **Validation rules table:** every input field → type, format, length, range, sanitization
- **Error codes:** new registry entries (internal code → public key → HTTP)
- **Logging plan:** events, levels, fields
- **Complexity notes:** Big-O for non-trivial algorithms
- Security (authn/authz per endpoint), performance budgets, risks, alternatives
- ADR for every significant decision or standard exception
- Migration mode: migration-plan.md (forward, rollback, backfill, index build strategy, lock impact, dry-run steps)

**jarvis-devops** — tools: Read, Write, Glob, Grep. Modes: design, deploy. Runs only when `has_infra_change` is true, alongside `jarvis-architect` in architecture and alongside `jarvis-release` in release. Plans infrastructure; never writes CI files, IaC or manifests.
- design → `infra-plan.md`: current pipeline/IaC/manifest inventory (each cited `file:line`), pipeline stages with triggers, blocking dependencies `[OPS-01]` and permission scopes `[OPS-03]`, IaC resources and remote locked state `[OPS-05]`, deploy strategy with readiness gate `[OPS-08]`, concurrency group `[OPS-13]` and reversing command `[OPS-07]`, secrets by name and store only `[OPS-04]`, RED metrics/log fields/trace propagation `[OPS-09]`, one alert row per SLO signal with owner and runbook `[OPS-10]`, resource requests and limits `[OPS-12]`.

**jarvis-planner** — tools: Read, Write, Glob, Grep. Writes plan.md: tasks `T-xxx` with `layer` (backend|frontend|shared), story refs, files/areas, `depends_on`, size S/M/L, done criteria, test expectations. **jarvis-dev-backend** — tools: Read, Write, Edit, MultiEdit, Glob, Grep, Bash. Implements exactly one task. Reads: structure, coding-go, api, database, caching, error-handling, logging, security, performance, testing.

Must not: touch files outside the task scope (log unavoidable ones), change the API contract without spec, swallow errors, log secrets/PII.

**jarvis-dev-frontend** — tools: Read, Write, Edit, MultiEdit, Glob, Grep, Bash. Implements exactly one task. Reads: structure, coding-react, api, security, performance, error-handling, logging, testing, ux-spec.
Must: feature-folder structure; TanStack Query for server state; Zod schemas for forms and API responses; display errors through the public message-key map, never raw backend messages; no `dangerouslySetInnerHTML` without DOMPurify; virtualize lists > 100 items; route-level code splitting; accessibility per ux-spec; Vitest + Testing Library tests; run `jarvis.js check frontend` and lint before returning; append impl-log entry.

**jarvis-tester** — tools: Read, Write, Edit, Glob, Grep, Bash. Modes: standard, regression, parity, benchmark, exploit, migration. Writes test-plan.md (TC ↔ AC table), test code, test-report.md (results, coverage).
Must: every AC ≥ 1 TC; negative tests for validation, sanitization, error-code mapping, authz; Go integration tests with testcontainers (MySQL, MongoDB); frontend component tests; Playwright e2e for critical flows; benchmarks (Go bench or k6) when an NFR has a perf budget; regression mode proves the test fails on the pre-fix code (evidence in report); migration mode tests up, down and idempotency.
Must not: modify production code — report defects as `D-xxx`.

**Reviewers** — tools: Read, Grep, Glob, Bash (`git diff`, `git log`, `git show` only). Input scope: `git diff <base>...HEAD`. Output: `review/<reviewer>.md` with a findings table and a machine block:
```json
{"reviewer":"security","verdict":"pass|fail","findings":[{"id":"F-SEC-001","severity":"critical","file":"apps/api/internal/otp/handler.go","line":42,"rule":"SEC-04","issue":"...","fix":"..."}]}
```

Every finding cites a rule ID and file:line. Reviewers never edit code.

Deploy gated on verification `[OPS-01]`, pinned actions and images `[OPS-02]`, explicit minimal CI permissions `[OPS-03]`, no committed or echoed secret `[OPS-04]`, resources in IaC with remote locked state `[OPS-05]`, apply only from CI on the default branch `[OPS-06]`, reversible deploy `[OPS-07]`, distinct probes gating the rollout `[OPS-08]`, RED metrics and trace propagation `[OPS-09]`, alerts with owner and runbook `[OPS-10]`, one promoted artifact `[OPS-11]`, resource limits `[OPS-12]`, concurrency guard `[OPS-13]`, lockfile-based install `[OPS-14]`. Findings are `F-OPS-NNN`.

**jarvis-qa** — tools: Read, Write, Glob, Grep, Bash (test commands only). **jarvis-staff** — tools: Read, Write, Glob, Grep, Bash (`git log`, `git show`, `git diff`, `grep` only). Modes: full, delta, area. The only agent with no work item and no gate: it reviews the codebase as a whole over time, where the four reviewers each judge one diff. Runs on demand via `/jarvis-health`, when the newest report exceeds `staff_review.max_age_days`, and before a minor or major release (`REL-13`).

## 12. Standards (`.jarvis/standards/`)

Every standards file: rules with IDs, each marked **MUST** or **SHOULD**, each with a ✅/❌ example, and a final "Exceptions" note (ADR required).

### structure.md
```
apps/
  web/src/
    app/                    # routing, providers, layouts
    features/<feature>/     # components, hooks, api, schemas, __tests__
    shared/                 # ui wrappers, hooks, utils
    lib/                    # api client, error-message map, logger
  api/
    cmd/<service>/main.go
    internal/
      <domain>/             # handler.go, service.go, repository_mysql.go,
                            # repository_mongo.go, model.go, dto.go,
                            # validation.go, cache.go, *_test.go
      platform/             # config, db, cache, logger, apperror, middleware
    api/openapi.yaml
    migrations/mysql/  migrations/mongo/
packages/
  errors/                   # registry.yaml + generated Go/TS
  ui/                       # shared components
  api-client/               # generated from openapi.yaml
  config/                   # shared eslint/tsconfig
docs/ work/ adr/ architecture/
```
Rules: dependency direction handler → service → repository; DB access only in repository; no business logic in handlers; interfaces defined by the consumer; a domain never imports another domain's repository (go through its service); no circular imports.

### coding-go.md
gofmt + golangci-lint clean (enable gosec, errcheck, gocyclo ≤ 15, bodyclose, sqlclosecheck, prealloc); `context.Context` first param with timeouts; wrap internal errors with `%w`, convert to AppError at service boundary; no panic in request path; no global mutable state; goroutines have lifecycle (errgroup, bounded); maps for lookups instead of nested loops; preallocate slices; no `fmt.Print*`; `// Complexity: O(...)` on non-trivial loops; table-driven tests.

### coding-react.md
TypeScript strict, no `any`; feature folders; TanStack Query for server state, no server data in global store; Zod for forms and API responses; errors via message-key map; no `dangerouslySetInnerHTML` without DOMPurify; stable keys; `useMemo`/`useCallback` only when measured; virtualization for long lists; route-level code splitting; ESLint (react-hooks, jsx-a11y).

### api.md
REST; OpenAPI is the source of truth; `/v1` versioning; cursor pagination mandatory for lists with max page size; idempotency keys for non-idempotent creates where duplicates matter; success envelope `{ "data": ..., "meta": ... }`; error envelope `{ "error": { "code": "<public key>", "request_id": "<id>", "fields": [...] } }` (`fields` only for validation, using contract field names); timeouts and rate limits documented per endpoint.

### database.md
MySQL: **MUST NOT use JOIN** — use denormalized columns or two-step fetch with batched `WHERE id IN (...)` (≤ 1000 per batch); every WHERE/ORDER BY combination covered by an index with EXPLAIN evidence (no full scan on tables > 1k rows); no `SELECT *`; parameterized queries only; no functions on indexed columns in WHERE; golang-migrate with up + down; short transactions; utf8mb4.
MongoDB: **MUST NOT use `$lookup`**; embed vs reference decision documented; every query/sort index-covered following ESR (Equality, Sort, Range) with `explain()` showing IXSCAN; `$jsonSchema` validation per collection; projections always; no unbounded arrays; TTL indexes for expiring data; indexes created by migration scripts; user input never used directly as a query object.
Both: Query-Index Matrix maintained in `docs/architecture/query-index-matrix.md`.

### caching.md
Cache-aside default; key format `<service>:<domain>:<entity>:<id>:v<n>`; TTL mandatory with jitter; invalidate on write; stampede protection (singleflight); user-scoped keys for per-user data; never cache secrets; on cache failure degrade to DB and log warn; hit/miss metrics; which endpoints must be cached is declared in tech-spec.

### performance.md
State Big-O for non-trivial code; no O(n²)+ on unbounded input when a better approach exists; no redundant iterations (merge passes); no query/HTTP/cache calls inside loops (batch); pagination for all lists; bounded concurrency; timeouts on all external calls; budgets from config (`api_p95_ms`, `web_lcp_ms`); PERF items require before/after evidence.

### security.md
Validate every external input (type, length, format, range, enum) at the backend boundary — frontend validation is UX only; sanitize: parameterized SQL, reject `$`-prefixed and dotted keys in Mongo inputs, output encoding, bluemonday for rich text; authn on all non-public endpoints and authz per resource (IDOR checks); secrets only from env/secret manager; no internal error details to clients (registry only); PII masking in logs; rate limiting on auth/OTP endpoints; security headers, CORS allowlist; argon2id/bcrypt for passwords; file upload type/size checks; dependency scanning in CI; PDPA considerations for personal data.

### error-handling.md
See section 13.

### logging.md
Structured JSON via Go `slog`. Required fields: `ts, level, msg, service, component, request_id, trace_id, user_id (ID only), error_code`. MUST log: request start/end in middleware (method, route, status, latency); every error once at the boundary where it becomes an AppError (with internal code, cause, stack) — no duplicate logging up the stack; external call failures; cache failures (warn); auth failures; state-changing business events (audit). Levels: debug (dev detail), info (business events), warn (degraded/recoverable), error (failed request/operation). MUST NOT log passwords, tokens, OTPs, full card/ID numbers or full PII. Frontend reports errors with `request_id` to the logging endpoint.

### testing.md
Test pyramid; coverage minimums from config; Go `Test<Func>_<Scenario>` table-driven; integration via testcontainers; mocks through interfaces; frontend Testing Library (behavior, not implementation); Playwright e2e for critical paths; each AC ≥ 1 TC; negative tests for validation, sanitization, authz, error mapping; benchmarks when an NFR has a budget.

### documentation.md
English, concise, tables over prose, Mermaid only, IDs everywhere, templates define length.

### git.md
Branch `<type>/<ID>-<slug>`; Conventional Commits `feat(otp): add verify endpoint [FEAT-012][T-003]`; roughly one task per commit; PR template includes work item ID and gate status.

### devops.md
Area `OPS`, 14 MUST rules, read by `jarvis-devops` and `jarvis-review-devops` and applied to any file the `has_infra_change` flag covers (CI/CD, IaC, Dockerfiles, k8s/Helm, deploy and monitoring config). OPS-01 verify before deploy · 02 pin every action, image and tool version · 03 explicit minimal CI permissions · 04 secrets from a secret store, never the repo · 05 all infrastructure in code with locked remote state · 06 plan in the PR, apply only from CI on the default branch · 07 reversible deploy with a named strategy and rollback · 08 readiness and liveness probes gate the rollout · 09 RED metrics, structured logs and trace propagation · 10 one alert per SLO signal, each with an owner and a runbook · 11 config per environment, one artifact promoted · 12 resource requests and limits on every workload · 13 deploy concurrency guard, idempotent re-runs · 14 reproducible, lockfile-based builds.

## 13. Error Handling and Code Registry

### 13.1 Registry `packages/errors/registry.yaml`
```yaml
- code: INTERNAL_ERROR        # internal, unique, UPPER_SNAKE
  public: bmsg_error          # safe key returned to client
  http: 500
  level: error
  description: Unexpected failure
- code: USER_NOT_FOUND
  public: bmsg_error
  http: 404
  level: warn
  description: User id not found in repository
- code: VALIDATION_FAILED
  public: bmsg_validation_error
  http: 400
  level: info
  description: Request failed validation
- code: OTP_INVALID
  public: bmsg_otp_invalid
  http: 400
  level: info
  description: OTP mismatch or expired
```

### 13.2 Rules
- Default public key is `bmsg_error`. A specific public key is allowed only when the user can act on it (validation, auth, own-resource not found) and it reveals no internals (no table/column names, SQL, stack, variable names).
- Clients receive only `{ "error": { "code": "<public>", "request_id": "..." } }` (+ `fields` for validation using contract field names).
- Full detail (internal code, cause chain, stack, context) is logged once with the same `request_id`.
- Go flow: repository returns wrapped raw errors → service converts to `apperror.New(apperror.CODE, cause)` → response middleware writes public envelope and logs internal detail. Unknown errors → `INTERNAL_ERROR`.
- Codegen (`npm run gen:errors` or `go generate`) produces Go constants and a TS map; frontend maps public key → i18n text.
- CI/validate: codes unique; every code used in code exists in the registry; no string literal error codes in handlers.

## 15. Checklists (`.jarvis/core/checklists/`)

Format: `## Blocking` and `## Advisory`; every item has an ID (`REQ-01`), is verifiable yes/no, and names the evidence to check. Minimum Blocking items:

- **intake (INT):** type justified; all flags set; title ≤ 8 words.
- **brief (BRF):** problem stated without solution; ≥ 1 metric with target; impacted systems listed.
- **requirements (REQ):** every FR has priority; every Must FR referenced by ≥ 1 US; every US has ≥ 1 AC in Given/When/Then; negative/error AC present for every input-taking story; ACs testable (no vague words); NFRs include performance, security, logging; Out of Scope present; no TBD.
- **business-flow (BF):** every US appears in a flow or sequence; every BR traced; edge cases include failure paths; diagrams render as valid Mermaid.
- **ux (UX):** every screen has all states; every input field has validation mapped to AC; errors use public keys only; accessibility section complete.
- **investigation (INV):** evidence cites file:line/logs/measurements; root cause (not symptom); mode-specific sections complete.
- **architecture (ARC):** every FR mapped; no JOIN/`$lookup` in design (or ADR); every query in Query-Index Matrix has an index; cache design for declared read-heavy paths; validation rules for every input field; error codes listed with public keys; logging plan covers every error boundary; Big-O noted for non-trivial logic; authz per endpoint; OpenAPI delta valid; migration plan has rollback (if db change).
- **plan (PLN):** every US covered; one layer per task; dependencies acyclic; each task has done criteria and test expectations.
- **implement (IMP):** all deterministic checks pass; lint rules pass; every task done; impl-log complete; registry updated for new codes; Query-Index Matrix updated.
- **test (TST):** every AC has ≥ 1 TC; all tests pass; coverage ≥ config; negative tests for validation/sanitization/authz; mode-specific evidence (regression fail-before, parity, benchmark, migration up/down).
- **review (REV):** all enabled reviewers ran; no blocking-severity findings open; every finding cites rule + file:line.
- **qa (QA):** traceability matrix complete; every AC passing; NFR evidence present; Go/No-Go stated.
- **release (REL):** rollback steps; migration order; config changes; monitoring queries; forced gates listed.
- **postmortem (PM):** timeline; root cause; action items created as work items.

### 16.3 `guard.js` (PreToolUse / PostToolUse hook)
Reads hook JSON from stdin (`tool_name`, `tool_input.file_path`, `tool_input.command`). Block with exit 2 + stderr reason.
- **G1** Block Write/Edit to `.jarvis/state/**`, `.jarvis/core/**`, `.jarvis/scripts/**`, `.claude/**` unless env `JARVIS_DEV=1` (framework development mode).
- **G2** Block Bash commands invoking human-only CLI (`approve|force|skip|reopen|park|unpark`).
- **G3** If `gates.source_guard`: block edits under `apps/**` and `packages/**` unless some active item is in `implement` (any file) or `test` (test files only).
- **G4** Block edits to migration folders unless the active item has `has_db_change=true`.
- **G5** Block reading or editing `.env*` and secret files.
- **Post mode:** format the edited file (gofmt / prettier) and run lint rules on it; report violations to Claude via stderr with exit 2 so it fixes them.
