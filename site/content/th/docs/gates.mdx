## ลำดับการตรวจของ gate

ทุก phase ต้องผ่านขั้นตอนเดียวกันนี้ก่อน phase ถัดไปจะเริ่มได้

<Steps>
<Step title="Script gate">
`jarvis.js validate <ID> <phase>` ตรวจส่วนที่เช็กด้วยกฎตายตัวได้ ได้แก่ front matter, heading ที่ต้องมี,
รูปแบบ ID, การอ้างอิงไปยัง artifact ต้นทาง, จำนวน coverage และใน phase implement จะรัน check command
ที่ตั้งค่าไว้กับกฎ lint ด้วย
</Step>
<Step title="Agent gate">
agent `jarvis-gatekeeper` อ่าน checklist ของ phase และ artifact ต้นทาง แล้วตรวจรายการ Blocking
ทุกข้อโดยต้องมีหลักฐาน เช่น บรรทัดที่อ้างถึง ID หรือแถวในตาราง คำตอบแบบ "เกือบเสร็จแล้ว" ไม่ผ่าน
</Step>
<Step title="Human approval">
ใช้เฉพาะ phase ที่อยู่ใน `gates.human_approval` (ค่าเริ่มต้นคือ requirements, ux,
architecture และ release) แต่ละ workflow กำหนดค่านี้ใหม่เป็นราย phase ได้ ดู
[การตั้งค่า](/docs/configuration)
</Step>
</Steps>

ถ้า script gate หรือ agent gate ไม่ผ่าน ปัญหาที่เจอจะถูกส่งกลับไปให้ agent ตัวเดิม และตัวนับจำนวนครั้งจะเพิ่มขึ้น
เมื่อครบ `gates.max_retries` (ค่าเริ่มต้น 3) orchestrator จะหยุดลองใหม่และแสดง Gate Failure Menu แทน

ลองเล่นดูเอง เลือกว่าแต่ละ gate ผ่านหรือไม่ผ่าน แล้วดู phase เคลื่อนไป

## Gate Failure Menu

orchestrator แสดงเมนูนี้ออกมาตามนี้ทุกตัวอักษร

```text
⚠️  GATE FAILED: FEAT-012 / review (attempt 3/3)
Blocking issues:
  - [F-SEC-001][critical] Raw DB error returned in POST /v1/otp response
  - [F-PERF-002][major] Query inside loop in otp/service.go:88
Risk if forced: <one or two lines>
Options:
  1) Retry — send issues back to the agent (resets attempts)
  2) Fix manually, then run: /jarvis FEAT-012
  3) Force pass (human only, audited):
     ! npm run -s jarvis -- force FEAT-012 review --reason "<why>"
  4) Park work item:
     ! npm run -s jarvis -- park FEAT-012 --reason "<why>"
```

ถ้าขอให้ Claude force ผ่าน gate ในจังหวะอื่น Claude จะแสดงเมนูเดียวกันนี้พร้อมปัญหาที่ค้างอยู่ตอนนั้น
Claude ไม่รัน `force` เองเด็ดขาด

## สถานะของ phase

<StatusMachine />

| Status | ความหมาย | ใครเป็นคนตั้ง |
|---|---|---|
| `pending` | ยังไม่เริ่ม | CLI (ค่าเริ่มต้น) |
| `in_progress` | agent กำลังทำงาน | Claude ผ่าน `set` |
| `gate_failed` | script gate หรือ gatekeeper gate ไม่ผ่าน | Claude ผ่าน `set` |
| `passed` | ผ่านทั้งสอง gate แล้ว | Claude ผ่าน `set` |
| `approved` | คนอนุมัติ phase ที่ `passed` แล้ว | คน ผ่าน `approve` |
| `forced` | คน force ผ่าน gate ที่ไม่ผ่าน | คน ผ่าน `force` |
| `skipped` | ข้าม phase ที่ไม่บังคับ | CLI (เมื่อ flag เป็น false) หรือคน ผ่าน `skip` |
| `blocked` | รอคำตอบของ open question หรือรอสิ่งที่อยู่นอกระบบ | Claude ผ่าน `set` |
| `parked` | พักทั้ง work item ไว้ | คน ผ่าน `park` |

phase ถัดไปจะเริ่มได้เมื่อ phase ก่อนหน้าอยู่ในสถานะ `approved` (ถ้าต้องมีการอนุมัติ), `passed`
(ถ้าไม่ต้องอนุมัติ), `forced` หรือ `skipped` (เฉพาะ phase ที่ไม่บังคับ)

## ความรุนแรง

reviewer, gatekeeper และ `qa` ใช้ระดับความรุนแรงชุดเดียวกันนี้

<div className="not-prose flex flex-wrap gap-2 my-4">
<StatusBadge kind="severity" value="critical" label="critical" />
<StatusBadge kind="severity" value="major" label="major" />
<StatusBadge kind="severity" value="minor" label="minor" />
<StatusBadge kind="severity" value="info" label="info" />
</div>

- **critical** ช่องโหว่ด้านความปลอดภัย, ข้อมูลหายหรือเสียหาย, acceptance criterion ไม่ผ่าน,
  ส่งรายละเอียด error ภายในกลับไปให้ client, นำ input จากภายนอกไปใช้โดยไม่ validate หรือ sanitize
- **major** ละเมิดกฎ MUST ข้อใดก็ตาม, ใช้ SQL `JOIN` หรือ Mongo `$lookup` โดยไม่มี ADR, query ที่ไม่มี
  index รองรับ, เรียก query, HTTP หรือ cache ใน loop, ไม่มี log ที่ error boundary, error code ที่ไม่อยู่ใน
  registry, acceptance criterion ที่ไม่มี test
- **minor** ละเมิดกฎ SHOULD, การตั้งชื่อ, ความอ่านง่าย, โค้ดซ้ำเล็กน้อย
- **info** ข้อเสนอแนะ ไม่ต้องแก้ก็ได้

`review.block_on` ใน `jarvis.config.yaml` กำหนดว่า severity ระดับไหนจะทำให้ reviewer ตัดสินเป็น
`fail` ค่าเริ่มต้นคือ critical กับ major ส่วน minor และ info เป็นแค่คำแนะนำเสมอ

## การ force เมื่อ gate ไม่ผ่าน

force มีไว้ใช้ในกรณีพิเศษเท่านั้น ไม่ได้มีไว้เลี่ยงมาตรฐาน และเป็นคำสั่งที่คนต้องรันเอง `guard.js` บล็อก
ไม่ให้ Claude รันคำสั่งกลุ่มนี้ทุกตัว รวมถึง `force` ด้วย

```text
! npm run -s jarvis -- force FEAT-012 review --reason "hotfix window closes in 10 min"
```

- ต้องใส่ `--reason` ทุกครั้ง
- อะไรที่อยู่ใน `gates.non_forceable` ต้องใส่ `--accept-risk` เพิ่ม ค่าเริ่มต้นครอบคลุม security finding
  ระดับ critical และ acceptance criterion ที่ไม่ผ่านใน `qa`
- ระบบบันทึกเหตุผล, `user.name` ของ git, เวลา และ ID ของ finding ที่ยังไม่แก้ ลงใน audit log ของ
  work item
- ระบบสร้าง work item ประเภท `chore` ให้อัตโนมัติ พร้อมรายการ finding ที่ยังไม่แก้
- status report ทุกครั้งหลังจากนั้นจะแสดง `⚠️ <ID> has N forced gate(s): <phases>` และทั้ง
  `qa-report.md` กับ `release-notes.md` จะมีหัวข้อ **Forced Gates**

## Skip, reopen, park

คำสั่งกลุ่มนี้ก็เป็นคำสั่งที่คนต้องรันเองเช่นกัน `guard.js` บล็อกไม่ให้ Claude รัน

| คำสั่ง | ผลลัพธ์ |
|---|---|
| `skip <ID> <phase> --reason "<why>"` | ข้าม phase ที่ไม่บังคับ (phase ที่มี `optional_if_false` ใน workflow) |
| `reopen <ID> <phase>` | รีเซ็ต phase นั้นและทุก phase หลังจากนั้นกลับเป็น `pending` |
| `park <ID> --reason "<why>"` / `unpark <ID>` | พัก work item ทั้งชิ้นไว้ และกลับมาทำต่อ |

<Callout kind="warning" title="ทำไมต้องให้คนรันคำสั่งเหล่านี้เอง">
ถ้าอนุมัติงานของตัวเองได้ การอนุมัติก็ไม่มีความหมาย Jarvis จึงบังคับกฎนี้ที่ระดับ hook (กฎ G2 ของ
`guard.js`) แทนที่จะหวังให้ agent ทำตามคำสั่งเอง ตามหลักการ "ใช้ hook บังคับกฎที่ห้ามละเมิด" ในหน้า
[แนวคิดหลัก](/docs/concepts)
</Callout>
