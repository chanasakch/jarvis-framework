## Jarvis คืออะไร

Jarvis เป็นเฟรมเวิร์ก SDLC ที่ขับเคลื่อนด้วย AI และรันบน Claude Code มันส่งงานไปยัง specialist
subagent ตรวจสอบผลลัพธ์ทุกชิ้นเทียบกับมาตรฐานของทีมคุณเองผ่าน gate สามชั้น — สคริปต์ที่ตรวจแบบตายตัว
ตามด้วย gatekeeper agent แล้วจึงเป็นการอนุมัติโดยมนุษย์ในจุดที่สำคัญ — และบล็อกไม่ให้งานเดินหน้าต่อ
จนกว่าแต่ละ phase จะผ่าน Definition of Done ของตัวเอง

<Callout kind="note" title="ออกแบบมาสำหรับสแตกหนึ่ง แต่ไม่ได้ผูกติดกับมัน">
มาตรฐานที่มาพร้อมเฟรมเวิร์กเล็งไปที่ monorepo ที่มี frontend เป็น React + TypeScript และ backend
เป็น Go เชื่อมกับ MySQL และ MongoDB แต่กลไกหลัก — กฎที่มี ID กำกับ ตรวจสอบโดยสคริปต์และ agent —
ใช้ได้กับสแตกไหนก็ได้ มีแค่ไฟล์ `.jarvis/standards/*.md` เท่านั้นที่ผูกกับสแตกนี้โดยเฉพาะ และไฟล์
พวกนี้เป็นของโปรเจกต์ ทีมคุณแก้ไขได้เองโดยตรง
</Callout>

## ทำไมถึงมีเฟรมเวิร์กนี้

ถ้าปล่อยให้ AI coding agent ทำงานตามลำพัง มันจะเขียนโค้ดที่ดูน่าเชื่อถือแต่ไม่ตรงตามมาตรฐานของทีม —
`JOIN` ในจุดที่ตกลงกันแล้วว่าห้ามใช้ query ที่ไม่มี index รองรับ ส่ง error ดิบจากฐานข้อมูลตรงไปที่
เบราว์เซอร์ หรือ acceptance criterion ที่ไม่มี test รองรับ สิ่งเหล่านี้อ่านโค้ดครั้งเดียวไม่มีทางเห็น —
มันจะโผล่มาตอนเกิด incident หรือใน comment รีวิวที่ต้องเขียนซ้ำแบบเดิมทุกครั้ง

คำตอบของ Jarvis ตรงไปตรงมา: แปลงมาตรฐานทุกข้อให้เป็นกฎที่มี ID กำกับ (`.jarvis/standards/*.md`)
แล้วแปลงกฎทุกข้อให้เป็นสิ่งที่สคริปต์หรือ agent ตรวจสอบจริงก่อนที่งานจะเดินหน้าต่อได้ หลักการออกแบบ
10 ข้อนี้คือสิ่งที่ยึดทุกอย่างไว้ด้วยกัน:

1. **Orchestrator = slash command** `/jarvis` รันอยู่ใน session หลักของคุณ subagent ไม่สามารถ
   spawn subagent ต่อได้ ดังนั้นทุก handoff ต้องผ่านมันเสมอ
2. **File-based handoff** agent แลกเปลี่ยนกันด้วย path ของไฟล์ ไม่ใช่เนื้อหาที่ paste มา — artifact
   ทุกชิ้นอยู่ใน `docs/work/<ID>-<slug>/`
3. **Gate สามชั้น** สคริปต์ที่ตรวจแบบตายตัว ตามด้วย gatekeeper agent ที่ต้องมีหลักฐานประกอบ แล้วจึง
   เป็นมนุษย์สำหรับ phase ที่สำคัญ — ดู [เกต](/docs/gates)
4. **Hook บังคับใช้กฎที่ต้องไม่มีข้อยกเว้น** อะไรก็ตามที่ต้องไม่เกิดขึ้นเด็ดขาด — การแก้ไฟล์ของ
   framework การรันคำสั่งที่สงวนไว้สำหรับคนเท่านั้น การแตะ migration โดยไม่ประกาศ schema change
   ไว้ก่อน — จะถูก `guard.js` บล็อกก่อนที่ tool call จะรัน ไม่ใช่จับได้ทีหลัง
5. **Traceability ด้วย ID** `FR → US → AC → TC → code → release` — ทุก requirement, story,
   criterion, task และ finding มี ID กำกับ
6. **Configuration แทนที่จะ hardcode** workflow, gate, คำสั่ง และ threshold ทั้งหมดอยู่ใน
   `jarvis.config.yaml` และ `.jarvis/core/workflows/*.yaml` ไม่ใช่ logic ที่ฝังตายตัวในโค้ด
7. **ของ framework กับของโปรเจกต์แยกกันชัดเจน** `.jarvis/core`, `.jarvis/scripts`,
   `.claude/agents` และ `.claude/commands` จะถูกแทนที่ตอนอัปเกรด ส่วน `.jarvis/standards`,
   `jarvis.config.yaml` และ `CLAUDE.md` จะไม่ถูกแตะต้องเลย
8. **ทุกข้อยกเว้นต้องมี ADR** มาตรฐานข้อหนึ่งจะผ่อนปรนสำหรับกรณีเฉพาะได้ — แต่ข้อยกเว้นนั้นต้องถูก
   บันทึกไว้เป็นลายลักษณ์อักษรและอ้างอิง ID ของกฎนั้น
9. **เข้มงวดเป็นค่าเริ่มต้น** การ force ผ่าน gate ที่ล้มเหลวทำได้ แต่ต้องเป็นคนทำเท่านั้น ต้องมีเหตุผล
   ประกอบ ถูกบันทึกไว้ตรวจสอบ และสร้าง follow-up item ให้กับสิ่งที่ยังไม่ได้แก้
10. **วินัยเรื่องโทเค็น** artifact สั้นและเขียนเป็นภาษาอังกฤษ agent จะอ่านเฉพาะมาตรฐานที่ phase
    ของตัวเองต้องใช้จริงเท่านั้น

## เมื่อไหร่ที่ไม่ควรใช้

Jarvis มีต้นทุนจริง — คำถามตอน intake, phase ที่มี gate, การอนุมัติโดยมนุษย์ในบาง phase — ซึ่งคุ้มค่า
กับงานที่อยู่ยาวกว่าหนึ่ง session: ฟีเจอร์ใหม่, การแก้บั๊กที่ต้องหา root cause จริงจัง, อะไรก็ตามที่แตะ
production มันคือเครื่องมือที่ผิดสำหรับการแก้ typo บรรทัดเดียว การทดลองที่จะทิ้งไปในที่สุด หรือการ
เปลี่ยนแปลงที่ไม่มีโค้ดเลย สำหรับงานวิจัยที่ผลลัพธ์คือการตัดสินใจ ไม่ใช่การ merge โค้ด ให้ใช้ work
type `spike` — มันจบหลัง investigation โดยไม่มี phase implement เลย
