## Jarvis คืออะไร

Jarvis เป็นเฟรมเวิร์ก SDLC ที่ใช้ AI ขับเคลื่อน รันบน Claude Code โดยจะส่งงานแต่ละส่วนให้ subagent
เฉพาะทาง แล้วตรวจผลงานทุกชิ้นกับมาตรฐานของทีมผ่าน gate สามชั้น ชั้นแรกเป็นสคริปต์ที่ตรวจตามกฎตายตัว
ชั้นที่สองเป็น gatekeeper agent และชั้นสุดท้ายคือคนอนุมัติ ใน phase ที่จำเป็นต้องมีคนดู phase ไหนยังไม่ผ่าน
Definition of Done ของตัวเอง งานก็ไปต่อไม่ได้

มาตรฐานที่ให้มาในชุดเขียนไว้สำหรับ monorepo ที่ frontend เป็น React + TypeScript และ backend เป็น Go
ใช้ MySQL กับ MongoDB แต่กลไกหลัก คือกฎที่มี ID กำกับและให้สคริปต์กับ agent เป็นผู้ตรวจ ใช้กับสแตกไหนก็ได้
ส่วนที่ผูกกับสแตกนี้มีแค่ไฟล์ `.jarvis/standards/*.md` ซึ่งเป็นไฟล์ของโปรเจกต์ ทีมแก้เองได้เลย
</Callout>

## ทำไมถึงมีเฟรมเวิร์กนี้

ถ้าปล่อยให้ AI coding agent ทำงานเองโดยไม่มีใครคุม โค้ดที่ได้มักดูดีแต่ไม่ตรงมาตรฐานของทีม เช่น ใช้
`JOIN` ทั้งที่ตกลงกันไว้แล้วว่าห้ามใช้ เขียน query ที่ไม่มี index รองรับ ส่ง error ดิบจากฐานข้อมูลไปถึงเบราว์เซอร์
หรือมี acceptance criterion ที่ไม่มี test เลย ปัญหาแบบนี้อ่านโค้ดรอบเดียวมักไม่เห็น กว่าจะเจอก็ตอนเกิด incident
หรือไม่ก็ต้องมาเขียนคอมเมนต์รีวิวเรื่องเดิมซ้ำแล้วซ้ำอีก

Jarvis แก้ด้วยการเขียนมาตรฐานทุกข้อเป็นกฎที่มี ID กำกับ (`.jarvis/standards/*.md`) แล้วให้สคริปต์หรือ agent
ตรวจกฎทุกข้อก่อนงานจะไปต่อได้ ทั้งระบบตั้งอยู่บนหลักการออกแบบ 10 ข้อ

1. **Orchestrator = slash command** `/jarvis` รันอยู่ใน session หลักของคุณ เนื่องจาก subagent สร้าง
   subagent ต่อเองไม่ได้ การส่งต่องานทุกครั้งจึงต้องผ่าน `/jarvis`
2. **ส่งต่องานผ่านไฟล์** agent ส่ง path ของไฟล์ให้กัน ไม่แปะเนื้อหาส่งต่อกัน artifact ทุกชิ้นเก็บอยู่ใน
   `docs/work/<ID>-<slug>/`
3. **Gate สามชั้น** สคริปต์ที่ตรวจตามกฎตายตัว ต่อด้วย gatekeeper agent ที่ต้องแนบหลักฐาน แล้วจึงให้คนตรวจใน
   phase ที่จำเป็น ดูรายละเอียดที่ [เกต](/docs/gates)
4. **ใช้ hook บังคับกฎที่ห้ามละเมิด** `guard.js` จะบล็อกการกระทำที่ห้ามเกิดขึ้นตั้งแต่ก่อน tool call รัน
   ไม่ต้องรอไปจับได้ทีหลัง ตัวอย่างเช่น การแก้ไฟล์ของ framework การรันคำสั่งที่คนต้องรันเอง และการแก้
   migration โดยไม่ได้ประกาศ schema change ไว้ก่อน
5. **ย้อนรอยได้ด้วย ID** `FR → US → AC → TC → code → release` requirement, story, criterion,
   task และ finding ทุกตัวมี ID กำกับ
6. **ใช้ config แทนการ hardcode** workflow, gate, คำสั่ง และ threshold ทั้งหมดกำหนดไว้ใน
   `jarvis.config.yaml` และ `.jarvis/core/workflows/*.yaml` ไม่ได้เขียนฝังไว้ในโค้ด
7. **แยกไฟล์ของ framework กับไฟล์ของโปรเจกต์ชัดเจน** ตอนอัปเกรด `.jarvis/core`, `.jarvis/scripts`,
   `.claude/agents` และ `.claude/commands` จะถูกเขียนทับ แต่ `.jarvis/standards`,
   `jarvis.config.yaml` และ `CLAUDE.md` จะอยู่เหมือนเดิม
8. **ข้อยกเว้นทุกข้อต้องมี ADR** ผ่อนมาตรฐานบางข้อให้กรณีเฉพาะได้ แต่ต้องเขียนข้อยกเว้นนั้นเป็นเอกสาร
   และอ้าง ID ของกฎที่ยกเว้น
9. **เข้มงวดเป็นค่าเริ่มต้น** force ผ่าน gate ที่ไม่ผ่านได้ แต่คนต้องเป็นคนสั่งเอง ต้องระบุเหตุผล ระบบจะบันทึก
   ไว้ให้ตรวจย้อนหลัง และสร้าง follow-up item สำหรับเรื่องที่ยังค้างอยู่
10. **ประหยัดโทเค็น** artifact เขียนสั้นและเป็นภาษาอังกฤษ agent อ่านเฉพาะมาตรฐานที่ phase ของตัวเอง
    ต้องใช้

## เมื่อไหร่ที่ไม่ควรใช้

Jarvis มีต้นทุนเพิ่ม ทั้งคำถามตอน intake, phase ที่ต้องผ่าน gate และการรอคนอนุมัติในบาง phase ต้นทุนนี้คุ้ม
กับงานที่ใช้เวลาเกินหนึ่ง session เช่น ฟีเจอร์ใหม่ การแก้บั๊กที่ต้องหา root cause ให้ชัด หรืองานที่กระทบ
production แต่ไม่เหมาะกับการแก้คำผิดบรรทัดเดียว การทดลองที่ทำแล้วทิ้ง หรือการเปลี่ยนแปลงที่ไม่มีโค้ด
ถ้าเป็นงานค้นคว้าที่ผลลัพธ์คือการตัดสินใจ ไม่ใช่โค้ดที่จะ merge ให้ใช้ work type `spike` ซึ่งจบหลัง
investigation และไม่มี phase implement
