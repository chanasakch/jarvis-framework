## SDLC คืออะไร

SDLC ย่อมาจาก software development lifecycle หรือวงจรการพัฒนาซอฟต์แวร์ คือชุดขั้นตอนที่พาไอเดียหนึ่งเรื่อง
ไปเป็นซอฟต์แวร์ที่ลูกค้าใช้งานได้จริง ตั้งแต่ทำความเข้าใจปัญหา จนถึงการปล่อยและดูแลหลังปล่อย

ไม่มีใครสร้างบ้านโดยลงเสาเข็มก่อนรู้ว่าเจ้าของอยากได้บ้านแบบไหน ซอฟต์แวร์ก็เช่นกัน
ทีมที่ทำงานเป็นขั้นตอนไม่ได้ช้ากว่า เพียงแต่ถูกบังคับให้ตอบคำถามที่ใช่ ในเวลาที่ยังแก้ได้ถูก

## ทำไมธุรกิจต้องสนใจ

ผู้บริหารและเจ้าของธุรกิจไม่ต้องอ่านโค้ด แต่ต้องรับผลของมันทั้งเรื่องเวลา งบ และความเชื่อมั่นของลูกค้า
SDLC คือสิ่งที่ทำให้สามเรื่องนี้คาดการณ์ได้ แนวคิดที่ยอมรับกันกว้างในวงการซอฟต์แวร์คือ ยิ่งพบปัญหาช้า ยิ่งแก้แพง
เพราะสิ่งที่ต้องแก้ไม่ได้หยุดอยู่ที่ความเข้าใจ แต่ลามไปถึงเอกสาร แบบ โค้ด การทดสอบ และข้อมูลของลูกค้า

<CostCurve />

ขั้นตอนของ SDLC จึงเป็นจุดตรวจเพื่อให้พบปัญหาในขั้นที่ยังแก้ถูก ไม่ได้มีไว้เพิ่มเอกสาร
สิ่งที่ธุรกิจได้กลับมาคือความคาดการณ์ได้ เพราะรู้ว่างานอยู่ตรงไหน และความรับผิดชอบที่ไล่ย้อนได้
เพราะรู้ว่าใครตัดสินใจอะไรด้วยเหตุผลอะไร

## จากไอเดียถึงลูกค้า ทีละขั้น

ตัวอย่างสมมติต่อไปนี้ตามหนึ่งไอเดียผ่านหกขั้น แต่ละขั้นมีคำถามทางธุรกิจที่ต้องตอบ สิ่งที่ได้ออกมา
และสิ่งที่มักพังถ้าข้ามไป เลื่อนลงเพื่อดูเส้นทางไล่ไปทีละขั้น

หกขั้นข้างบนไม่ได้แปลว่างานต้องเดินเป็นเส้นตรงครั้งเดียวจบ ทีมแต่ละทีมเลือกจังหวะต่างกัน
สามแนวทางที่พบบ่อยคือ

<ModelsCompare />

ไม่มีแนวทางไหนถูกที่สุด หลายทีมผสมกัน เช่น ทำงานเป็นรอบสั้นแบบ Agile และใช้ DevOps ทำให้การปล่อยเป็นเรื่องปกติ
สิ่งที่เหมือนกันทุกแนวทางคือยังต้องผ่านหกขั้นเดิม ต่างกันที่งานวนกลับมาบ่อยแค่ไหน

## Jarvis เข้ามาช่วยตรงไหน

ทั้งหมดข้างบนเป็นเรื่องของ SDLC โดยทั่วไป ไม่เกี่ยวกับเครื่องมือใด Jarvis เป็น framework ที่ทำงานบน Claude Code
โดยรับงานเป็นหน่วยที่เรียกว่า work item แล้วพาแต่ละชิ้นผ่านขั้นตอนเดิมนี้ ทุกขั้นมีเจ้าของเป็น agent
มีผลลัพธ์เป็นไฟล์ และมีการตรวจก่อนไปขั้นถัดไป รายการต่อไปนี้จับคู่ปัญหาที่ทีมทั่วไปเจอบ่อยกับสิ่งที่ Jarvis ทำ

<JarvisBridge />

Jarvis ไม่ได้บังคับโมเดลการทำงาน ภายในงานหนึ่งชิ้น phase เดินตามลำดับ แต่ทีมเปิดงานชิ้นเล็ก ๆ ต่อเนื่องกี่ชิ้นก็ได้
จึงใช้ในจังหวะแบบ Agile ได้ และคำสั่ง `/jarvis-portfolio` ช่วยให้เห็นภาพรวมเมื่อมีหลายชิ้นเปิดพร้อมกัน
ส่วนที่เหลือของหน้านี้ลงรายละเอียดว่า Jarvis ทำงานในแต่ละขั้นอย่างไร

## ภาพรวมของวงจร

ทุก work item ที่ Jarvis รับไปทำจะวนรอบเดียวกัน คือทำความเข้าใจคำขอ ระบุให้ชัด ออกแบบ ลงมือสร้าง
พิสูจน์ว่าใช้ได้ แล้วปล่อยงาน สิ่งที่ต่างกันระหว่างประเภทงานคือ phase ไหนถูกรัน hotfix ข้ามขั้นออกแบบ
ส่วน spike จบหลัง investigation แผนภาพด้านล่างวาดตามงานประเภท `feature` ทุก agent ทุกผลลัพธ์
และทุกจุดอนุมัติในภาพอ่านมาจากไฟล์ workflow ของ framework เอง จึงไม่เพี้ยนไปจากสิ่งที่ Jarvis ทำจริง

<SdlcLifecycle />

เลือกขั้นที่อยากดู หรือปล่อยให้ตัวอย่างเล่นเอง ตัวอย่างจะหยุดชั่วคราวเมื่อเอาเมาส์วางหรือโฟกัสที่ภาพ
หยุดถาวรเมื่อเลือกขั้นเอง และมีปุ่มหยุดให้กดได้ตลอด

## กระบวนการนี้มีไว้ทำไม

ทีมที่ข้ามขั้นตอนของ SDLC ก็ยังได้ซอฟต์แวร์ แต่การตัดสินใจไปกระจายอยู่ในแชท requirement เพี้ยนไปเรื่อย ๆ
ตั้งแต่ข้อความแรกจนถึง commit สุดท้าย และคุณภาพของ review ขึ้นอยู่กับว่าวันนั้นใครว่าง

Jarvis ให้ทุกขั้นมีสามอย่าง

- **เจ้าของ** มี agent หนึ่งตัวรับผิดชอบขั้นนั้น และอ่านเฉพาะไฟล์ที่ได้รับมอบหมาย
- **ผลลัพธ์** ทุกขั้นจบด้วยไฟล์ใน `docs/work/<ID>-<slug>/` อยู่ใน git และมี ID ที่ขั้นถัดไปอ้างกลับมาได้
- **การตรวจ** สคริปต์กับ gatekeeper agent ตรวจผลลัพธ์กับ checklist ก่อนที่ขั้นถัดไปจะเริ่มได้
  ดู [เกต](/docs/gates)

## ใครทำอะไร

อ่านรายการนี้เป็นการจับคู่ระหว่างทีมที่คุณจะจ้าง กับ agent ที่ครอบคลุมแต่ละบทบาท
ทีมเล็กมักมีวิศวกรคนเดียวสวมหลายหมวก Jarvis ยังแยกหมวกออกจากกัน แต่ละหมวกจึงมี checklist ของตัวเอง

<RoleMap />

[เอเจนต์](/docs/agents) รวม tools, inputs และ outputs ของทุก agent ไว้ บทบาท project manager
ครอบคลุมด้วยคำสั่ง เพราะข้อมูลที่รายงานเป็นสถานะจริงที่อยู่บนดิสก์อยู่แล้ว สคริปต์อ่านให้
โมเดลจึงไม่ต้องเดาสถานะเอง

## จุดที่คุณยังคุมอยู่

Jarvis ไม่อนุมัติงานของตัวเอง ค่าเริ่มต้นจะหยุดรอคน 4 จุด กำหนดด้วย `gates.human_approval` ใน `jarvis.config.yaml`

| การอนุมัติ | สิ่งที่คุณรับรอง | ใช้เมื่อ |
|---|---|---|
| `requirements` | PRD และ user story รวมถึง acceptance criterion ทุกข้อ | เสมอ |
| `ux` | หน้าจอ สถานะ การตรวจสอบข้อมูล และ accessibility | งานนั้นมี UI |
| `architecture` | tech spec, API contract และ ADR | เสมอ |
| `release` | release notes, runbook และแผน rollback | เสมอ |

การอนุมัติเป็นคำสั่งที่คุณต้องรันเอง Claude รันไม่ได้ `guard.js` บล็อก `approve`, `force`, `skip`,
`reopen`, `park` และ `unpark` ตั้งแต่ก่อนคำสั่งถูกเรียก

```bash
npm run -s jarvis -- approve FEAT-012 requirements
```

ถ้าอยากอ่านรายการ task ก่อนเริ่มเขียนโค้ด ให้เพิ่ม `plan` ใน `gates.human_approval`

## หนึ่งคำขอตั้งแต่ต้นจนจบ

นี่คือหน้าตาของหนึ่งคำขอจากฝั่งคุณ item นี้คือ `FEAT-012` และทุกไฟล์อยู่ใน `docs/work/FEAT-012-otp-login/`

<Steps>
<Step title="เริ่ม">
คุณพิมพ์ `/jarvis` ตามด้วยคำขอ orchestrator จัดคำขอเข้าประเภทงาน ถามคำถามเรื่อง flag ไม่เกิน 5 ข้อ
แล้วเขียน `intake.md` จากนั้น analyst เขียน `brief.md`
</Step>
<Step title="ระบุให้ชัด">
agent ฝั่ง product owner เขียน `prd.md` และ `stories.md` ส่วน business analyst เพิ่ม `business-flow.md`
ระบบจะหยุดให้คุณอนุมัติ `requirements` ถ้างานมี UI จะมี `ux-spec.md` ตามมาและต้องอนุมัติแยกอีกครั้ง
</Step>
<Step title="ออกแบบ">
architect เขียน `tech-spec.md`, `api-contract.yaml` และ ADR สำหรับทุกการตัดสินใจสำคัญ
พร้อม `migration-plan.md` เมื่อมีการแก้ schema และ `infra-plan.md` เมื่อ item ตั้ง `has_infra_change`
คุณอนุมัติ `architecture` จากนั้น planner เขียน `plan.md`
</Step>
<Step title="สร้าง">
ทุก task ใน `plan.md` ส่งให้ agent ฝั่ง backend หรือ frontend ครั้งละหนึ่ง task พอจบแต่ละ task
CLI จะรัน check ของ layer นั้นและบันทึกผลต่อท้าย `impl-log.md`
</Step>
<Step title="พิสูจน์">
tester เขียน `test-plan.md` และ `test-report.md` reviewer รันพร้อมกันและเขียน `review/<reviewer>.md`
ซึ่ง CLI รวมเป็น `review-report.md` finding ที่บล็อกจะกลายเป็น task แบบ `FIX-` แล้วงานย้อนกลับไป build
จากนั้น QA เขียน `qa-report.md` พร้อม traceability matrix และคำตัดสิน Go/No-Go
</Step>
<Step title="ปล่อยงาน">
release agent เขียน `release-notes.md` เพิ่ม `runbook.md` เมื่องานแก้ฐานข้อมูล และเพิ่มรายการใน CHANGELOG
คุณอนุมัติ `release`
</Step>
</Steps>

## ย้อนรอยจากคำขอถึง release

ทุก requirement, story, criterion, test และ finding มี ID และทุกผลลัพธ์ที่ตามมาอ้างกลับไปหาของก่อนหน้า
นี่คือสิ่งที่ทำให้ QA พิสูจน์ได้ว่าครอบคลุม แทนที่จะแค่บอกว่าครอบคลุม

<TraceChain />

สายนี้คือสิ่งที่ `qa-report.md` บันทึกเป็น traceability matrix และ script gate ก็อ่านมันด้วย
Must requirement ที่ไม่มี story อ้างถึง, acceptance criterion ที่ไม่มี test case และแถวใน matrix ที่ไม่ผ่าน
แต่ละกรณีทำให้ phase ไม่ผ่าน

## วงที่ทำให้เป็นวงจร

วงจรนี้คือการวน ต่อไปนี้คือทางที่งานวนกลับมาใน Jarvis

| วง | อะไรเป็นตัวกระตุ้น | เกิดอะไรขึ้น |
|---|---|---|
| Gate retry | script check หรือ gatekeeper ตัดสินว่า phase ไม่ผ่าน | agent ตัวเดิมได้รับรายการปัญหากลับไปแก้ ซ้ำได้ถึง `gates.max_retries` (ค่าเริ่มต้น 3) จากนั้นคุณเลือกได้ว่าจะ retry, แก้เอง, force ผ่านพร้อมเหตุผล หรือ park item |
| Review loop-back | reviewer รายงาน finding ที่ระดับบล็อก | item กลับไป build พร้อม task แบบ `FIX-` หนึ่งตัวต่อหนึ่ง finding |
| Reopen | phase ที่อนุมัติไปแล้วพบว่าผิด | คุณรัน `reopen` ซึ่งรีเซ็ต phase นั้นและทุก phase หลังจากนั้น |
| Postmortem | ปล่อย hotfix แล้ว | phase postmortem บันทึก timeline แบบไม่กล่าวโทษใคร และ action item กลายเป็น work item ตามงาน |
| Codebase health | report ล่าสุดเก่ากว่า `staff_review.max_age_days` (ค่าเริ่มต้น 30 วัน) | status line เตือน และ `/jarvis-health` ตรวจ architecture drift กับ tech debt ทั้ง repo |
| Portfolio | มี work item ที่ยังทำอยู่มากกว่าหนึ่งตัว | `/jarvis-portfolio` แสดง phase ของแต่ละ item สิ่งที่มันรออยู่ และไฟล์ที่สอง item วางแผนจะแก้ตรงกัน |

<Callout kind="note" title="การ force ถูกบันทึกไว้เสมอ">
เมื่อ gate ถูก force Jarvis จะเก็บว่าใครสั่ง เมื่อไร และเพราะอะไร เปิด chore item ตามงานสำหรับ finding ที่ยังค้าง
และระบุ gate ที่ถูก force ไว้ทั้งใน `qa-report.md` และ `release-notes.md`
</Callout>
