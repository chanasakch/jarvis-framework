## การติดตั้งสำหรับทีม

ทุกคนในทีมติดตั้งแบบเดียวกัน รันครั้งเดียวต่อรีโป

```bash
npx github:chanasakch/jarvis-framework init --name jarvis     # or --name ops, --name sdlc, …
cd .jarvis && npm install                   # one dependency: yaml
node .jarvis/scripts/jarvis.js doctor       # tools, paths, error registry
```

`--name` กำหนด prefix ของ slash command และ agent เช่น `--name ops` จะได้ `/ops`, `/ops-init`
และ agent ชื่อ `ops-architect` ส่วน path ภายใน (`.jarvis/`, `jarvis.config.yaml`) ใช้ชื่อเดิม
ไม่ว่าจะตั้ง prefix เป็นอะไร

`init` **ไม่เขียนทับไฟล์ที่เป็นของทีมคุณ** รันซ้ำได้ไม่มีปัญหา ไฟล์ของ framework
จะอัปเดตเป็นเวอร์ชันล่าสุด ส่วนมาตรฐาน, `jarvis.config.yaml` และ `CLAUDE.md` ของคุณจะอยู่เหมือนเดิม
ติดตั้งเสร็จแล้วให้ restart Claude Code เพื่อโหลด hook, agent และคำสั่งใหม่ จากนั้นรัน
`/jarvis-init` เพื่อสแกนรีโปและเขียน `.jarvis/project/context.md`

ให้ commit `.claude/`, `.jarvis/` และ `docs/work/` รวมทั้ง `.jarvis/state/` ด้วย state ของ work item
แต่ละรายการเป็นไฟล์ JSON เล็ก ๆ หนึ่งไฟล์กับ audit log ที่เขียนต่อท้ายอย่างเดียว สองคนที่ทำคนละ
item จึงไม่ชนกัน

## gate ของ CI

workflow สำเร็จรูป (`project-templates/.github/workflows/jarvis.yml`) รัน job `gate` กับทุก PR
ที่จะเข้า `main` และมี job `backend` กับ `frontend` แยกรันคู่กันไป ซึ่งจะรันก็ต่อเมื่อมีไฟล์
`apps/api/go.mod` หรือ `apps/web/package.json` หลัง checkout และ `npm install` ใน
`.jarvis/` แล้ว job `gate` จะตรวจตามขั้นตอนนี้

```bash
node .jarvis/scripts/jarvis.js ci --base origin/main
node .jarvis/scripts/audit.js
node --test ".jarvis/scripts/test/*.test.js"
```

`jarvis.js ci` อ่านชื่อ branch ปัจจุบัน ดึง work item ID ออกมา (ตาม pattern `[A-Z]+-\d{3}`)
แล้วจะ fail ถ้าเข้าข้อใดข้อหนึ่งต่อไปนี้

- work item นั้นมี phase ที่สถานะไม่ใช่ `approved`, `passed`, `forced` หรือ `skipped`
- `lint` (รันแบบ `--changed`) เจอการละเมิดระดับ `critical` หรือ `major`
- `packages/errors/registry.yaml` parse ไม่ผ่าน, มีรายการที่ขาด field บังคับ (`code`, `public`,
  `http`, `level`, `description`) หรือมี `code` ซ้ำ

ถ้าใช้ GitLab มีไฟล์ให้ที่ `project-templates/ci/gitlab-ci.example.yml`

## CODEOWNERS

`project-templates/.github/CODEOWNERS` ส่งงานรีวิวไปให้กลุ่มที่ดูแลส่วนที่ถูกแก้
การผ่อนมาตรฐานหรือการแก้ framework จึงไม่หลุดเข้าไปได้เพราะมีคนที่ไม่เกี่ยวข้องกดอนุมัติ

| Path | Reviewer | เหตุผล |
|---|---|---|
| `.jarvis/standards/` | tech leads | การผ่อน rule ต้องให้เจ้าของเซ็นรับ อนุมัติจากใครก็ได้ไม่พอ |
| `.jarvis/core/`, `.jarvis/scripts/`, `.claude/agents/`, `.claude/commands/`, `.claude/settings.json` | tech leads | เป็นของ framework ปกติจะเปลี่ยนผ่าน `upgrade` ไม่ได้แก้ด้วยมือ |
| `packages/errors/registry.yaml` | tech leads + frontend | เปลี่ยน public error key เท่ากับเปลี่ยน API แบบ breaking กับทุก client |
| `jarvis.config.yaml` | tech leads | เป็นตัวกำหนดว่าใครผ่อน gate ได้ |
| `docs/architecture/query-index-matrix.md` | tech leads + DBA | เป็นหลักฐานเรื่อง index ที่มาตรฐานฐานข้อมูลอ้างถึง |

template ใส่ชื่อทีมตัวอย่างไว้ (`@your-org/tech-leads`, `@your-org/frontend`,
`@your-org/dba`) ให้เปลี่ยนเป็นชื่อทีมจริงก่อนเปิด branch protection

## การอัปเกรด

```bash
npx github:chanasakch/jarvis-framework upgrade
node .jarvis/scripts/audit.js                 # framework is internally consistent
node --test ".jarvis/scripts/test/*.test.js"  # scripts still behave
```

`upgrade` ไล่ดูทุกไฟล์ที่มากับ framework ไฟล์ไหนใหม่ก็เขียนลงไป ไฟล์ไหนเปลี่ยนก็แทนที่
ไฟล์ไหนเหมือนเดิมก็ปล่อยไว้ จากนั้นเขียน `.jarvis/VERSION` ใหม่ คำสั่งนี้แตะเฉพาะ path
ที่เป็นของ framework คือ `.jarvis/core/`, `.jarvis/scripts/`, `.claude/agents/`,
`.claude/commands/`, `.claude/settings.json` แล้วพิมพ์สรุปว่าไฟล์ไหนเพิ่ม ไฟล์ไหนอัปเดต
และไฟล์ไหนไม่เปลี่ยน

`upgrade` ไม่แตะไฟล์ที่เป็นของโปรเจกต์เลย ได้แก่ `jarvis.config.yaml`, `CLAUDE.md`,
`.jarvis/standards/**`, `.jarvis/project/**` และ `packages/errors/registry.yaml`

ถ้าเวอร์ชันเก่าเคยมี agent หรือ command ที่เวอร์ชันนี้ไม่มีแล้ว `upgrade` จะรายงานไว้ใต้หัวข้อ
"not shipped by this version" โดยไม่ลบทิ้ง เพราะทีมอาจเอาไปต่อยอดไว้แล้ว จะลบหรือไม่ให้ทีมตัดสินใจเอง
อัปเกรดเสร็จแล้วให้ restart Claude Code เพื่อให้เห็นการเปลี่ยนแปลง

## การเสนอเปลี่ยนแปลงมาตรฐาน

มาตรฐานอยู่ในรีโปของคุณ ทีมจึงแก้ได้เองโดยไม่ต้องแตะ framework

1. เปิด PR แก้ไฟล์ใน `.jarvis/standards/`
2. ถ้า rule นั้นตรวจด้วยเครื่องได้ ให้แก้ `lint-rules.yaml` ใน PR เดียวกัน
3. **ถ้าผ่อนหรือลบ rule ต้องมี ADR เพิ่ม** ไว้ใน `docs/adr/` โดยระบุ rule ID, เหตุผล,
   ขอบเขต และวันหมดอายุ
4. `CODEOWNERS` จะส่ง PR ไปให้กลุ่มที่ดูแล `.jarvis/standards/` ตามตารางข้างบน

รายการ rule ID ทั้งหมดดูได้ที่ [มาตรฐาน](/docs/standards) หน้านั้นอธิบายกลไกขอยกเว้นเป็นกรณีไปด้วย
(`jarvis-ignore` คู่กับ ADR ที่ได้รับการยอมรับแล้ว) ใช้ตอนที่โค้ดบรรทัดเดียวต้องทำต่างจาก rule
โดยไม่ต้องแก้ตัว rule

## แก้ปัญหาเบื้องต้น

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| `G1 BLOCKED` ตอนแก้ `.jarvis/core` หรือ `.claude` | path เหล่านั้นเป็นของ framework | ถ้ากำลังพัฒนาตัว framework เอง ให้เปิด Claude Code ด้วย `JARVIS_DEV=1` |
| คำสั่งหรือ agent หายไปหลังอัปเกรด | Claude Code โหลดสิ่งเหล่านี้ตอนเริ่ม session | restart Claude Code |
| CI fail แต่ไม่มี phase ไหนติดปัญหา | `lint` หรือการตรวจ error registry ไม่ผ่าน | รัน `jarvis.js lint --changed` ในเครื่องเพื่อดู finding |
