## Orchestrator

`/jarvis` รันอยู่ใน session หลักของ Claude Code เสมอ ไม่เคยรันใน subagent เพราะ subagent สร้าง
subagent ต่อเองไม่ได้ การมอบงานทุกครั้งจึงต้องผ่าน orchestrator ตัว orchestrator เองไม่ทำงานของ phase
ไหนเลย ยกเว้น intake อย่างเดียว (จัดประเภท work item และถามคำถามเรื่อง flag)

phase อื่นทั้งหมด orchestrator จะอ่านผลจาก `jarvis.js next <ID> --json` แล้วนำมาทำเป็น
**Handoff Brief** ซึ่งเป็นข้อมูลอย่างเดียวที่ phase agent ได้รับ

```text
HANDOFF
work_item: FEAT-012 (feature) "OTP login"
phase: architecture | mode: full
flags: has_ui=true has_db_change=true has_mysql=true has_mongo=false
read:
  - docs/work/FEAT-012-otp-login/prd.md
  - docs/work/FEAT-012-otp-login/stories.md
  - .jarvis/project/context.md
standards: [.jarvis/standards/api.md, .jarvis/standards/database.md]
template: .jarvis/core/templates/tech-spec.md
checklist: .jarvis/core/checklists/architecture.md
write:
  - docs/work/FEAT-012-otp-login/tech-spec.md
task: (implement only) T-003
previous_gate_issues: none | [list]
user_answers: none | [list]
```

`read`, `standards`, `template`, `checklist` และ `write` คัดมาจาก `jarvis.js next` ตรงตัว
orchestrator ไม่เติมอะไรเพิ่ม ถ้า agent ต้องใช้ไฟล์ที่ไม่อยู่ในรายการนี้ ต้องขอผ่าน `open_questions`
จะไปอ่านไฟล์นั้นเองไม่ได้

<Callout kind="note" title="ทำไม brief ไม่แนบเนื้อหา artifact ไปด้วย">
สิ่งที่ส่งข้ามระหว่าง agent มีแค่ path ของไฟล์ ไม่มีการแปะข้อความส่งต่อกัน ดูหัวข้อ "การส่งต่องานแบบ file-based" ด้านล่าง
</Callout>

## Agent

agent ทุกตัวอยู่ใน `.claude/agents/jarvis-*.md` และมีโครงเหมือนกัน คือ YAML frontmatter
(`name`, `description`, `tools`, `model`) ตามด้วยหัวข้อชุดเดิมทุกครั้ง ได้แก่ `Role`, `Modes` (เฉพาะ phase
ที่มีมากกว่าหนึ่งโหมด), `Inputs`, `Outputs`, `Process`, `Must`, `Must Not`, `Self-Check` และ
`Return Format` ตัวอย่างเช่น `jarvis-po` ประกาศ `tools: Read, Write, Glob, Grep` กับ
`model: inherit` และในส่วน `Must Not` ห้ามออกแบบวิธีแก้ และห้ามใส่รหัส error ภายในลงใน acceptance
criterion ที่ผู้ใช้มองเห็น ส่วน `jarvis-architect` รันด้วย `model: opus` และมี `Modes` เป็น `full`,
`lite` และ `migration`

ก่อนส่งผลกลับ agent ทุกตัวจะรัน `Self-Check` ของตัวเองกับ checklist ของ phase และไม่ว่าจะอยู่ phase ไหน
ทุกตัวจะส่งผลกลับเป็นบล็อกนี้

```text
RESULT
status: DONE | BLOCKED
artifacts: [paths]
summary: <≤5 lines>
open_questions: [Q-001: ...] | none
self_check: pass | [failed item IDs]
```

`DONE` คือส่งงานคืนให้ orchestrator เพื่อเข้า Gate Protocol ส่วน `BLOCKED` แปลว่า agent ต้องการคำตอบ
ที่มีแต่คนเท่านั้นตอบได้ agent จะไม่เดาเอง

## คำสั่ง

Jarvis แบ่งคำสั่งเป็นสองกลุ่ม กลุ่มแรกคือ slash command (`/jarvis`, `/jarvis-status`,
`/jarvis-new`, `/jarvis-run`, `/jarvis-review`, `/jarvis-init`) ซึ่ง Claude เป็นคนรัน ใช้เดิน intake
ทำงานต่อจากที่ค้างไว้ และรัน phase กลุ่มที่สองคือคำสั่ง CLI `approve`, `force`, `skip`, `reopen`,
`park` และ `unpark` ซึ่งเป็นคำสั่งที่คนต้องรันเอง `guard.js` จะบล็อกไม่ให้ Claude รันคำสั่งพวกนี้
(ดูหัวข้อ "Hooks") orchestrator จึงทำได้แค่แสดงคำสั่งให้คุณเอาไปรันเอง

ที่ต้องแบ่งแบบนี้เพราะ subagent คุยกับคุณโดยตรงไม่ได้ เมื่อ phase agent ต้องการการตัดสินใจที่คนเท่านั้น
ตัดสินได้ ก็จะส่ง `BLOCKED` พร้อม `open_questions` กลับมา แล้ว orchestrator จะถามคุณใน session หลัก
ด้วยเหตุผลเดียวกัน การอนุมัติจึงเป็นคำสั่ง CLI ที่คุณรันเอง agent อนุมัติงานแทนคุณไม่ได้ ดูรายการคำสั่งทั้งหมด
พร้อมตัวอย่างได้ที่ [คำสั่ง](/docs/commands)

## กฎและมาตรฐาน

กฎที่ agent อ่านเก็บอยู่ในสองไดเรกทอรี และมีเจ้าของต่างกัน

| ไดเรกทอรี | เจ้าของ | เก็บอะไร |
|---|---|---|
| `.jarvis/core/rules/` | Framework | `orchestration.md` (โปรโตคอลที่อธิบายด้านบน), `conventions.md` (ID, front matter, phase status, severity) |
| `.jarvis/standards/` | ทีมของคุณ | `structure.md`, `coding-go.md`, `coding-react.md`, `api.md`, `database.md` และไฟล์อื่น ๆ กฎแต่ละข้อมี ID prefix เช่น `DB-01` หรือ `SEC-07` |

`.jarvis/core/` จะถูกเขียนทับทุกครั้งที่อัปเกรด ทีมจึงไม่ควรแก้ไฟล์ในนั้น ส่วน `.jarvis/standards/`
เป็นของคุณ กฎ MUST ทุกข้อในนั้นคือสิ่งที่ reviewer, gatekeeper และ `jarvis.js lint` ใช้ตรวจจริง
ดูรายการกฎทั้งหมดได้ที่ [มาตรฐาน](/docs/standards)

## Gate

ทุก phase ต้องผ่านสามชั้นเดียวกันก่อน phase ถัดไปจะเริ่มได้

1. **script gate** (`jarvis.js validate`) ที่ตรวจตามกฎตายตัว
2. **agent gate** (`jarvis-gatekeeper`) ที่ตรวจ artifact กับ checklist ของ phase โดยต้องมีหลักฐานประกอบ
3. **การอนุมัติจากคน** เฉพาะ phase ที่อยู่ใน `gates.human_approval`

ถ้า gate ไม่ผ่าน งานจะถูกส่งกลับไปให้ agent ตัวเดิมพร้อมรายการปัญหา เมื่อครบ `gates.max_retries`
แล้ว orchestrator จะหยุดลองใหม่และแสดง Gate Failure Menu แทน รายละเอียดโปรโตคอล หน้าตาของเมนู
และกฎการ force อยู่ที่ [เกต](/docs/gates)

## State

state ของ work item แต่ละตัวเก็บอยู่ในไฟล์เดียวที่ commit เข้า git คือ `.jarvis/state/<ID>.json`
คู่กับ `.jarvis/state/<ID>.audit.jsonl` ที่เขียนต่อท้ายอย่างเดียว บันทึก JSON หนึ่งบรรทัดทุกครั้งที่สถานะเปลี่ยน
(`{ts, actor, action, phase, from, to, detail}`) เมื่อแยกไฟล์ตาม item คนสองคนที่ทำคนละ item
ก็จะไม่ conflict กันใน git และเพราะ state อยู่ใน git ใครจะดูว่า item ไหนไปถึงไหนแล้วก็ดูได้เลย
ไม่ต้องถามใคร

สถานะของ phase มีได้เฉพาะค่าเหล่านี้

## Hooks

`guard.js` เป็น hook แบบ `PreToolUse`/`PostToolUse` ที่ทำงานทุกครั้งที่มีการเรียก tool
ใช้บังคับกฎข้างต้นในระดับ tool แทนที่จะหวังให้ agent ทำตามคำสั่งเอง

- **G1** บล็อก `Write`/`Edit` ใน `.jarvis/state/**`, `.jarvis/core/**`, `.jarvis/scripts/**`
  และ `.claude/**` ซึ่งเป็นไฟล์ของ framework
- **G2** บล็อกการเรียกผ่าน Bash ที่เป็นคำสั่ง CLI ที่คนต้องรันเอง (`approve`, `force`, `skip`,
  `reopen`, `park`, `unpark`)
- **G3** (source guard) บล็อกการแก้ไฟล์ใน `apps/**`/`packages/**` ยกเว้นเมื่อ item ที่ทำอยู่อยู่ใน phase
  `implement` (แก้ได้ทุกไฟล์) หรือ `test` (แก้ได้เฉพาะไฟล์ test)
- **G4** บล็อกการแก้โฟลเดอร์ migration ยกเว้นเมื่อ item ที่ทำอยู่มี `has_db_change=true`
- **G5** บล็อกการอ่านหรือเขียนไฟล์ `.env*` และไฟล์ secret อื่น ๆ

ถ้า `guard.js` มีบั๊กเอง จะ fail open คือปล่อยให้ tool call ผ่านไป แทนที่จะทำให้ session พังใช้ต่อไม่ได้
guard ที่ error จึงไม่ทำให้คุณทำงานต่อไม่ได้

## การส่งต่องานแบบ file-based

agent ส่ง path ของไฟล์ให้กัน ไม่แปะเนื้อหาส่งต่อกัน artifact ทุกชิ้นที่ phase สร้างขึ้นจะเก็บอยู่ใน
`docs/work/<ID>-<slug>/` (ผลรีวิวอยู่ในโฟลเดอร์ย่อย `review/`) agent ตัวถัดไปจะได้ path เหล่านี้ในรายการ
`read` ของ Handoff Brief ไม่ได้ข้อความตัวจริง วิธีนี้ทำให้ context เล็ก แต่ละ artifact รีวิวแยกกันใน git ได้
และ orchestrator ก็ส่งงานให้ agent ตัวใหม่ได้ทุก phase (และทุก task ระหว่าง implement) โดยไม่มีข้อมูลตกหล่น
