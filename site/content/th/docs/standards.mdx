## มาตรฐานเป็นของโปรเจกต์

Jarvis มาพร้อมชุดมาตรฐานสำหรับ monorepo ที่มี frontend เป็น React + TypeScript และ backend เป็น Go
เชื่อมต่อกับ MySQL, MongoDB และ Redis — แต่ไฟล์เหล่านี้อยู่ในรีโปของคุณเอง ที่
`.jarvis/standards/` และทีมของคุณแก้ไขได้โดยตรง ไม่มีอะไรใน `.jarvis/core` มา override มาตรฐานเหล่านี้
และ `jarvis-framework upgrade` จะไม่แตะไฟล์เหล่านี้เลย (ดู [การใช้งานแบบทีม](/docs/team))

ทุก rule มี ID กำกับ — `GO-01`, `DB-02`, `SEC-04` — เพื่อให้ finding จาก reviewer, การละเมิด lint หรือ
ADR ข้อยกเว้น สามารถอ้างอิงได้ตรงว่า rule ไหนที่ทำงาน ความรุนแรงของ rule เมื่อถูกละเมิด (critical,
major, minor, info) ถูกกำหนดไว้ที่เดียวคือใน `.jarvis/core/rules/conventions.md` §4 แล้วอ้างอิงใช้
ทุกที่ — ดูตารางความรุนแรงฉบับเต็มที่ [เกต](/docs/gates)

## ไฟล์มาตรฐาน

แต่ละไฟล์ถูกอ่านโดย agent ที่ทำงานในส่วนนั้น โดย review agent ที่ดูแลส่วนนั้น และโดยสคริปต์ `lint`
สำหรับ rule ที่ให้เครื่องตรวจได้ รายการนี้สร้างจาก `.jarvis/standards/` อัตโนมัติ จึงตรงกับไฟล์ที่ติดตั้งอยู่เสมอ

<StandardsIndex />

ถัดจากไฟล์เหล่านี้มี `lint-rules.yaml` ซึ่งไม่มี rule ของตัวเอง เป็นเพียง MUST rule ส่วนที่เครื่องตรวจได้
`jarvis.js lint` ใช้ไฟล์นี้ตรวจทีละบรรทัดด้วย regex

<Callout kind="note" title="ไม่ได้ผูกติดกับสแต็กนี้">
มีแค่ตัวไฟล์เองที่จำเพาะกับสแต็กนี้ ส่วนกลไก — rule ที่มี ID ตรวจสอบด้วยสคริปต์และ agent —
ใช้ได้กับสแต็กไหนก็ได้ แก้ไขหรือแทนที่ไฟล์เหล่านี้ให้เข้ากับสแต็กของคุณ
</Callout>

## MUST เทียบกับ SHOULD

ทุก rule ในไฟล์มาตรฐานมีรูปแบบเดียวกัน คือ ID, ชื่อ, tag `(MUST)` หรือ `(SHOULD)`, เนื้อหา rule
หนึ่งหรือสองประโยค ตามด้วยตัวอย่าง ✅ ที่ทำตาม rule และตัวอย่าง ❌ ที่ละเมิด rule — ตัวอย่างเช่น
`### GO-01 — gofmt and golangci-lint clean (MUST)` ใน `coding-go.md` หรือ
`### GIT-03 — Roughly one task per commit (SHOULD)` ใน `git.md`

- **MUST** — การละเมิดมีความรุนแรงอย่างน้อย `major` (ตาม `conventions.md` §4) และบล็อกเกตโดยค่าเริ่มต้น
- **SHOULD** — การละเมิดมีความรุนแรงระดับ `minor` จะถูก flag ใน review แต่ไม่บล็อกเกตด้วยตัวมันเอง
- คู่ ✅/❌ มีไว้เพื่อให้ reviewer หรือ gatekeeper agent จับคู่รูปแบบของ diff กับตัวอย่างที่เป็น
  รูปธรรมได้ แทนที่จะต้องตีความข้อความบรรยาย และเพื่อให้ `lint-rules.yaml` มีสิ่งที่ไม่กำกวมพอจะ
  แปลงเป็น regex

## อ่าน `lint-rules.yaml`

ไม่ใช่ทุก MUST rule ที่ตรวจได้ด้วย regex แต่ที่ตรวจได้จะอยู่ใน
`.jarvis/standards/lint-rules.yaml` รันด้วย `node .jarvis/scripts/jarvis.js lint` แต่ละรายการ
ระบุ rule ID ที่บังคับใช้, glob ที่ใช้ตรวจ, pattern และความรุนแรง — ตัวอย่างเช่น รายการ `DB-01`
จับคู่ `\bjoin\b` (ไม่สนตัวพิมพ์เล็กใหญ่) ทั่ว `apps/api/**/*.go` ที่ความรุนแรง `major` rule
ที่มีเครื่องหมาย `[ADDED]` ใน `desc` ของมัน ไม่ได้อยู่ใน spec เดิมของ framework — เป็นส่วนเสริมที่
พึ่งพา regex ควรตรวจสอบก่อนหาก team เจอ false positive

## การเสนอเปลี่ยนแปลงมาตรฐาน

มาตรฐานถูกออกแบบมาให้แก้ไขได้ วิธีเปลี่ยน:

1. เปิด PR แก้ไขไฟล์ภายใต้ `.jarvis/standards/`
2. ถ้า rule นั้นตรวจสอบได้ด้วยเครื่องจักร ให้อัปเดต `lint-rules.yaml` ใน PR เดียวกัน
3. `CODEOWNERS` จะส่ง PR ไปยังกลุ่มที่ดูแลมาตรฐาน — ดู [การใช้งานแบบทีม](/docs/team) สำหรับ
   path ที่แน่นอน
4. **การผ่อนปรนหรือลบ rule ต้องมี ADR ด้วย** ใน `docs/adr/` ระบุ rule ID, เหตุผล, ขอบเขต
   และวันหมดอายุ

การแก้ถ้อยคำหรือเพิ่ม rule ใหม่ไม่ต้องมี ADR — เฉพาะการผ่อนปรนหรือลบ rule ที่มีอยู่แล้วเท่านั้นที่ต้องมี

## กลไกข้อยกเว้น

ข้อยกเว้นเฉพาะจุดไม่จำเป็นต้องเปลี่ยนตัวมาตรฐานเอง ทุกไฟล์มาตรฐานจบด้วยข้อความเดียวกัน
คำต่อคำ (ตัวอย่างนี้มาจาก `caching.md` อ้างอิง `CACHE-03`):

> Any deviation from a rule in this file requires an ADR in `docs/adr/` that references the rule ID
> (e.g. `[CACHE-03]`) and is approved before the code merges.

เมื่อ ADR นั้นได้รับการยอมรับแล้ว ให้ suppress finding ของ lint จุดนั้นด้วยคอมเมนต์
`jarvis-ignore` บนบรรทัดที่ละเมิดหรือบรรทัดเหนือมันโดยตรง:

```go
// jarvis-ignore DB-01 ADR-0007
```

ไฟล์ YAML และ SQL ใช้ `-- jarvis-ignore ...` หรือ `# jarvis-ignore ...` แทน `//` linter จะ
resolve `ADR-0007` ไปยัง `docs/adr/ADR-0007-*.md` และจะยอมรับการ suppress ก็ต่อเมื่อไฟล์นั้น
มีอยู่จริง **และ** สถานะเป็น `accepted` — ADR ที่ยังไม่ resolve หรือแค่ถูกเสนอ จะทำให้การ
suppress นั้นถูกรายงานเป็นการละเมิด rule ที่มันพยายามจะปิดเสียงเอง

<Callout kind="warning" title="ADR ไม่ใช่ทางลัดข้ามการเช็คของ lint">
คอมเมนต์นี้จะทำงานก็ต่อเมื่อ ADR ถูกเขียนและได้รับการยอมรับแล้วเท่านั้น ไม่มีทางที่จะ suppress
finding ได้ด้วยการแก้ไขแค่ตัวมาตรฐาน, lint rule หรือคอมเมนต์ในโค้ดเพียงอย่างเดียว
</Callout>
