## มาตรฐานเป็นของโปรเจกต์

Jarvis มีมาตรฐานมาให้หนึ่งชุด ออกแบบสำหรับ monorepo ที่ frontend เป็น React + TypeScript และ backend
เป็น Go ใช้ MySQL, MongoDB และ Redis ไฟล์ทั้งหมดอยู่ในรีโปของคุณที่ `.jarvis/standards/`
ทีมแก้ได้เองโดยตรง ไม่มีอะไรใน `.jarvis/core` มาทับค่าเหล่านี้ และ `jarvis-framework upgrade`
ก็ไม่แตะไฟล์เหล่านี้เลย (ดู [การใช้งานแบบทีม](/docs/team))

ทุก rule มี ID กำกับ เช่น `GO-01`, `DB-02`, `SEC-04` เวลา reviewer เปิด finding, lint เจอการละเมิด
หรือมี ADR ขอยกเว้น ก็อ้างได้ตรงตัวว่าเป็น rule ข้อไหน ระดับความรุนแรงเมื่อละเมิด rule (critical,
major, minor, info) กำหนดไว้ที่เดียวใน `.jarvis/core/rules/conventions.md` §4 ที่อื่นอ้างถึงที่นี่ทั้งหมด
ตารางความรุนแรงฉบับเต็มอยู่ที่หน้า [Gate](/docs/gates)

## ไฟล์มาตรฐาน

ไฟล์แต่ละไฟล์มีผู้อ่านสามกลุ่ม คือ agent ที่ทำงานในด้านนั้น, review agent ที่รับผิดชอบด้านนั้น
และสคริปต์ `lint` สำหรับ rule ที่ตรวจด้วยเครื่องได้ รายการด้านล่างสร้างอัตโนมัติจาก `.jarvis/standards/`
จึงตรงกับไฟล์ที่ติดตั้งอยู่เสมอ

<StandardsIndex />

ข้าง ๆ ไฟล์เหล่านี้มี `lint-rules.yaml` ซึ่งไม่มี rule ของตัวเอง แต่เป็น MUST rule ชุดเดียวกับข้างบนเฉพาะข้อที่ตรวจด้วยเครื่องได้
`jarvis.js lint` อ่านไฟล์นี้แล้วตรวจด้วย regex บรรทัดละหนึ่งตัว

<Callout kind="note" title="ไม่ได้ผูกติดกับสแต็กนี้">
เฉพาะเนื้อหาในไฟล์เท่านั้นที่ผูกกับสแต็กนี้ ส่วนกลไก คือ rule ที่มี ID แล้วให้สคริปต์กับ agent ตรวจ
ใช้กับสแต็กไหนก็ได้ แก้หรือเขียนไฟล์ใหม่ให้เข้ากับสแต็กของคุณได้เลย
</Callout>

## MUST เทียบกับ SHOULD

rule ทุกข้อในไฟล์มาตรฐานเขียนแบบเดียวกัน คือมี ID, ชื่อ, tag `(MUST)` หรือ `(SHOULD)`, ตัว rule
หนึ่งหรือสองประโยค แล้วตามด้วยตัวอย่าง ✅ ที่ทำถูก และตัวอย่าง ❌ ที่ผิด rule เช่น
`### GO-01 — gofmt and golangci-lint clean (MUST)` ใน `coding-go.md` หรือ
`### GIT-03 — Roughly one task per commit (SHOULD)` ใน `git.md`

- **MUST**: ถ้าละเมิดจะมีความรุนแรงอย่างน้อยระดับ `major` (ตาม `conventions.md` §4) และค่าเริ่มต้นคือบล็อก gate
- **SHOULD**: ถ้าละเมิดจะมีความรุนแรงระดับ `minor` ขึ้นเป็นข้อสังเกตใน review แต่ลำพังตัวเองไม่บล็อก gate
- ตัวอย่าง ✅/❌ ช่วยให้ reviewer หรือ gatekeeper agent เทียบ diff กับตัวอย่างจริงได้
  ไม่ต้องตีความจากคำบรรยาย และทำให้ `lint-rules.yaml` มีรูปแบบที่ชัดพอจะเขียนเป็น
  regex ได้

## อ่าน `lint-rules.yaml`

MUST rule บางข้อตรวจด้วย regex ไม่ได้ ข้อที่ตรวจได้จะอยู่ใน
`.jarvis/standards/lint-rules.yaml` และรันด้วย `node .jarvis/scripts/jarvis.js lint` แต่ละรายการ
ระบุ rule ID ที่บังคับใช้, glob ของไฟล์ที่ตรวจ, pattern และความรุนแรง เช่น รายการ `DB-01`
หา `\bjoin\b` (ไม่สนตัวพิมพ์เล็กใหญ่) ในทุกไฟล์ `apps/api/**/*.go` ที่ความรุนแรง `major` ส่วน rule
ที่มี `[ADDED]` ใน `desc` ไม่ได้มาจาก spec ของ framework เอง แต่เพิ่มเข้ามาเพราะตรวจด้วย
regex ได้แม่นยำ ถ้าทีมเจอ false positive ให้เริ่มดูจาก rule กลุ่มนี้ก่อน

## การเสนอเปลี่ยนแปลงมาตรฐาน

มาตรฐานมีไว้ให้แก้ได้ ขั้นตอนมีดังนี้

1. เปิด PR แก้ไฟล์ใน `.jarvis/standards/`
2. ถ้า rule นั้นตรวจด้วยเครื่องได้ ให้แก้ `lint-rules.yaml` ใน PR เดียวกัน
3. `CODEOWNERS` จะส่ง PR ไปให้กลุ่มที่ดูแลมาตรฐานรีวิว path ที่ใช้จริงดูได้ที่
   [การใช้งานแบบทีม](/docs/team)
4. **ถ้าผ่อนหรือลบ rule ต้องมี ADR ด้วย** ไว้ใน `docs/adr/` โดยระบุ rule ID, เหตุผล, ขอบเขต
   และวันหมดอายุ

แก้ถ้อยคำหรือเพิ่ม rule ใหม่ไม่ต้องมี ADR ต้องมีเฉพาะตอนผ่อนหรือลบ rule ที่มีอยู่แล้ว

## กลไกข้อยกเว้น

การขอยกเว้นเป็นกรณีไปไม่ต้องแก้มาตรฐาน ไฟล์มาตรฐานทุกไฟล์ปิดท้ายด้วยประโยคเดียวกันทุกตัวอักษร
(ตัวอย่างนี้มาจาก `caching.md` ซึ่งอ้าง `CACHE-03`)

> Any deviation from a rule in this file requires an ADR in `docs/adr/` that references the rule ID
> (e.g. `[CACHE-03]`) and is approved before the code merges.

เมื่อ ADR ได้รับการยอมรับแล้ว ให้ปิด finding ของ lint เฉพาะจุดนั้นด้วยคอมเมนต์ `jarvis-ignore`
บนบรรทัดที่ละเมิด หรือบรรทัดที่อยู่เหนือขึ้นไปหนึ่งบรรทัด

```go
// jarvis-ignore DB-01 ADR-0007
```

ไฟล์ YAML และ SQL ใช้ `-- jarvis-ignore ...` หรือ `# jarvis-ignore ...` แทน `//` ตัว linter จะหา
`ADR-0007` จาก `docs/adr/ADR-0007-*.md` และยอมให้ปิด finding ก็ต่อเมื่อไฟล์นั้นมีอยู่จริง
**และ** มีสถานะเป็น `accepted` ถ้าหา ADR ไม่เจอหรือ ADR ยังเป็นแค่ข้อเสนอ lint จะรายงานคอมเมนต์นั้น
ว่าละเมิด rule เดียวกับที่พยายามปิดเสียง

<Callout kind="warning" title="ADR ไม่ใช่ทางลัดเลี่ยง lint">
คอมเมนต์นี้ใช้ได้หลังจากเขียน ADR และ ADR ได้รับการยอมรับแล้วเท่านั้น จะแก้แค่มาตรฐาน, lint rule
หรือคอมเมนต์ในโค้ดอย่างเดียวเพื่อปิด finding ไม่ได้
</Callout>
