## Jarvis ใช้กับสแตกอื่นที่ไม่ใช่ Go และ React ได้ไหม

ได้ กลไกของ Jarvis ไม่ผูกกับสแต็กไหน คือมี rule ที่มี ID ให้สคริปต์แบบ deterministic กับ
gatekeeper agent ตรวจ แล้วใช้ gate ตาม phase และความรุนแรง ส่วนที่ผูกกับสแต็กมีแค่ไฟล์มาตรฐาน
(`.jarvis/standards/*.md`) ซึ่งเขียนมาสำหรับ backend ที่เป็น Go และ frontend ที่เป็น React +
TypeScript ใช้ MySQL และ MongoDB ไฟล์เหล่านี้เป็นของโปรเจกต์ `init` และ `upgrade` ไม่แตะเลย
ทีมที่ใช้สแต็กอื่นจึงเขียนเนื้อหาใหม่ได้เลย (แก้รายการที่เกี่ยวข้องใน
`.jarvis/standards/lint-rules.yaml` ด้วย) ส่วนอื่นที่ต่อจากนั้น ทั้งขั้นตอนของ gate, ระดับความรุนแรง,
reviewer และ workflow ยังทำงานเหมือนเดิม ดู callout "Built for one stack, not locked to
it" ได้ที่ [ความรู้เบื้องต้น](/docs/introduction)

## ทำไม Claude ถึงอนุมัติงานของตัวเองไม่ได้

ถ้าคนเขียนงานอนุมัติงานตัวเองได้ การอนุมัติก็ไม่มีความหมาย `approve` (รวมทั้ง `force`, `skip`,
`reopen` และ `park`/`unpark`) เป็นคำสั่งที่คนต้องรันเอง และ rule G2 ใน `guard.js` จะบล็อก
การเรียก Bash ทุกครั้งที่พยายามรันคำสั่งเหล่านี้ ไม่ว่าจะเรียกผ่าน `jarvis.js
approve` หรือ `npm run -s jarvis -- approve` Claude จะพิมพ์คำสั่งที่ต้องรันออกมาแล้วให้คุณ
รันเอง ข้อนี้บังคับที่ระดับ hook ไม่ได้ฝากไว้กับคำสั่งใน prompt อย่างเดียว และ
`.jarvis/core/rules/orchestration.md` ก็เขียนไว้เป็นกฎเด็ดขาดที่ Claude ห้ามละเมิด
ตารางสถานะของ phase ฉบับเต็มอยู่ที่ [Gate](/docs/gates)

## ถ้า force gate ไปแล้วจะเกิดอะไรขึ้น

การ force คือการปล่อยให้ phase ที่ gate ไม่ผ่านจนครบจำนวน retry ไปต่อได้ เป็นคำสั่งที่คนต้องรันเอง
(`guard.js` บล็อกไม่ให้ Claude รัน) ต้องใส่ `--reason` ทุกครั้ง และมีบันทึกไว้เสมอ เหตุผล,
`user.name` ใน git ของคุณ, เวลา และ ID ของ finding ที่ยังไม่ได้แก้ จะลงไปอยู่ใน audit log
ของ work item แล้วระบบจะสร้าง work item ประเภท `chore` ขึ้นมาเองเพื่อตามเก็บสิ่งที่ค้างอยู่
รายงานสถานะทุกครั้งหลังจากนั้นจะแสดง
`⚠️ <ID> has N forced gate(s): <phases>` และทั้ง `qa-report.md` กับ `release-notes.md`
จะมีหัวข้อ **Forced Gates** เพิ่มขึ้นมา finding บางประเภท เช่น ปัญหาความปลอดภัยระดับ
critical หรือ acceptance criterion ที่ไม่ผ่านใน `qa` ต้องใส่ `--accept-risk` เพิ่มจาก
`--reason` ด้วย รายละเอียดทั้งหมดอยู่ที่ [Gate](/docs/gates)

## State ถูก commit เข้า git ด้วยไหม

ใช่ ตั้งใจให้เป็นแบบนั้น work item แต่ละรายการมีไฟล์ state แบบ JSON หนึ่งไฟล์ กับ audit
log ที่เขียนต่อท้ายอย่างเดียว อยู่ใต้ `.jarvis/state/` ให้ commit ทั้งสองไฟล์ไปพร้อมกับ
`.claude/`, `.jarvis/` และ `docs/work/` เนื่องจาก state แยกไฟล์ตาม work item ไม่ได้รวมอยู่
ในไฟล์เดียว สองคนที่ทำคนละ work item จึงไม่มีทางแก้บรรทัดเดียวกันจนชนกัน ห้ามแก้
ไฟล์เหล่านี้ด้วยมือ ต้องให้ CLI (`node .jarvis/scripts/jarvis.js set|task|flags|...`)
เขียนเท่านั้น และ rule G1 ใน `guard.js` จะบล็อกการแก้ `.jarvis/state/` ตรง ๆ

## bugfix กับ hotfix ต่างกันอย่างไร

ทั้งคู่ใช้แก้ defect เหมือนกัน แต่ใช้คนละสถานการณ์

| หัวข้อ | Bugfix (`BUG`) | Hotfix (`HOT`) |
|---|---|---|
| ความเร่งด่วน | ไม่เร่งด่วน | production มีปัญหา |
| Phase | intake → investigation → plan → implement → test → review → **qa** → release | intake → investigation → implement → test → review → release → **postmortem** |
| Phase QA | ต้องมี | ข้ามทั้งหมด |
| Postmortem | ไม่มี | มี แต่เป็น `deferrable: 3d` คือทำได้ภายใน 3 วันหลัง release |
| Reviewer ที่บล็อกได้ | ครบทั้งสี่ reviewer | เฉพาะ `security` และ `standards` |

hotfix ตัด phase QA ออกและเลื่อน postmortem ไปทำทีหลังเพื่อให้ออกได้เร็ว แต่ยังต้องผ่าน review
และยังต้องเขียน postmortem ภายใน 3 วันหลังแก้เหตุขัดข้องเสร็จ ดูรายละเอียด
ได้ที่ `.jarvis/core/workflows/bugfix.yaml` และ `.jarvis/core/workflows/hotfix.yaml`

## spike คืออะไร และทำไมถึงไม่มี phase implement

spike (`SPK`) คืองานค้นคว้าที่จำกัดเวลาไว้ ผลลัพธ์ที่ได้คือการตัดสินใจ
ไม่ใช่โค้ดที่ merge เข้าไป workflow ของ spike มีแค่สอง phase คือ `intake` และ `investigation`
โดย `investigation` จะได้ `spike-report.md` กับ ADR ฉบับร่าง แทน
`investigation.md` แบบปกติ ไม่มี phase `plan`, `implement`, `test`, `review`, `qa` หรือ
`release` เลย เพราะ spike ตั้งใจไม่ให้สร้าง production code ถ้าสรุปผลจาก spike แล้วว่า
ควรสร้างอะไรสักอย่าง ให้สร้าง work item ใหม่แยกด้วย `jarvis.js new`
ไม่ได้ทำต่อใน spike เดิม ดู [ความรู้เบื้องต้น](/docs/introduction) และ
`.jarvis/core/workflows/spike.yaml`

## กำหนดโมเดลแยกตาม agent เองได้ไหม

ได้ ตั้งผ่าน `models.overrides` ใน `jarvis.config.yaml`

```yaml
models:
  default: inherit
  overrides:
    jarvis-gatekeeper: opus
    jarvis-architect: opus
    jarvis-review-security: opus
    jarvis-release: haiku
```

`default: inherit` แปลว่า agent ที่ไม่ได้ override จะใช้โมเดลเดียวกับ session
Claude Code ที่คุณเปิดอยู่ ส่วน agent ที่อยู่ใน `overrides` จะใช้โมเดลที่ระบุไว้แทน
โดยตัวติดตั้งจะเขียนค่านี้ลงใน frontmatter ของ agent นั้น schema ส่วนอื่นของ config
ดูได้ที่ [การตั้งค่า](/docs/configuration)

## การ upgrade จะแตะต้อง standards ของเราไหม

ไม่ `npx jarvis-framework upgrade` แทนที่เฉพาะไฟล์ของ framework ได้แก่
`.jarvis/core/`, `.jarvis/scripts/`, `.claude/agents/` และ `.claude/commands/` แล้วพิมพ์
รายการที่เปลี่ยนออกมา ส่วน `.jarvis/standards/`, `jarvis.config.yaml`,
`.jarvis/project/` และ `CLAUDE.md` เป็นของโปรเจกต์ `init` และ `upgrade` ไม่เขียนทับเลย
ถึงค่าเริ่มต้นที่มากับ framework จะเปลี่ยนไปก็ตาม ดูว่าไฟล์ไหนเป็นของใครทั้งหมดได้ที่
[การใช้งานแบบทีม](/docs/team)
