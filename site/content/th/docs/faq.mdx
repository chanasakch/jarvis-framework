## Jarvis ใช้กับสแตกอื่นที่ไม่ใช่ Go และ React ได้ไหม

ได้ กลไกหลักของ Jarvis คือ กฎที่มี ID ตรวจสอบด้วยสคริปต์แบบ deterministic ร่วมกับ
gatekeeper agent แล้วเกตตาม phase และ severity ซึ่งไม่ผูกกับสแตกใดสแตกหนึ่งเลย ส่วนเดียว
ที่ผูกกับสแตกคือไฟล์ standards เอง (`.jarvis/standards/*.md`) ที่มาพร้อมค่าเริ่มต้นสำหรับ
backend ที่เขียนด้วย Go และ frontend ที่เป็น React + TypeScript คู่กับ MySQL และ MongoDB
ไฟล์เหล่านี้เป็นของโปรเจกต์เอง `init` และ `upgrade` จะไม่แตะต้องมันเลย ทีมที่ใช้สแตกอื่นจึง
แทนที่เนื้อหาในไฟล์เหล่านี้ได้โดยตรง (พร้อมทั้งรายการที่ตรงกันใน
`.jarvis/standards/lint-rules.yaml`) และทุกอย่างที่ต่อจากนั้น ทั้ง gate protocol, severity,
reviewer, workflow จะยังทำงานได้เหมือนเดิม ดู callout "Built for one stack, not locked to
it" ได้ที่ [ความรู้เบื้องต้น](/docs/introduction)

## ทำไม Claude ถึงอนุมัติงานของตัวเองไม่ได้

เพราะถ้าทำได้ ก็จะทำให้การอนุมัติหมดความหมายไปเลย `approve` (รวมถึง `force`, `skip`,
`reopen` และ `park`/`unpark`) อยู่ในรายการคำสั่งที่สงวนไว้สำหรับมนุษย์เท่านั้น และกฎ G2 ของ
`guard.js` จะสกัดการเรียก Bash ใด ๆ ที่พยายามรันคำสั่งเหล่านี้ ไม่ว่าจะเป็น `jarvis.js
approve` หรือ `npm run -s jarvis -- approve` Claude จะพิมพ์คำสั่งที่ถูกต้องออกมาแล้วให้คุณ
เป็นคนรันเอง กฎนี้ถูกบังคับใช้ที่ระดับ hook ไม่ใช่แค่คำสั่งในพรอมป์ เช่นเดียวกับที่
`.jarvis/core/rules/orchestration.md` กำหนดให้เป็นกฎตายตัวที่ Claude ต้องไม่ละเมิดเด็ดขาด
ดูตาราง phase-status แบบเต็มได้ที่ [เกต](/docs/gates)

## ถ้า force เกตไปแล้วจะเกิดอะไรขึ้น

การ force คือการทำให้เฟสที่เกตล้มเหลวจนถึงขีดจำกัดการรีทรายผ่านไปได้ เป็นคำสั่งสำหรับ
มนุษย์เท่านั้น (`guard.js` สกัด Claude ไม่ให้รันได้) ต้องระบุ `--reason` เสมอ และไม่มีทาง
เงียบเชียบ เพราะเหตุผล, `user.name` ของ git, เวลาที่ทำ และ ID ของ finding ที่ยังไม่ถูกแก้
จะถูกบันทึกลง audit log ของ work item พร้อมทั้งสร้าง work item ประเภท `chore` ตามมาโดย
อัตโนมัติเพื่อไล่ตามสิ่งที่ยังค้างอยู่ รายงานสถานะครั้งต่อ ๆ ไปจะแสดง
`⚠️ <ID> has N forced gate(s): <phases>` และทั้ง `qa-report.md` กับ `release-notes.md`
จะมีส่วน **Forced Gates** เพิ่มเข้ามา บาง finding เช่น finding ด้านความปลอดภัยระดับ
critical หรือ acceptance criterion ที่ไม่ผ่านใน `qa` จะต้องใส่ `--accept-risk` เพิ่มเติม
นอกเหนือจาก `--reason` ด้วย กลไกแบบเต็มอยู่ใน [เกต](/docs/gates)

## State ถูก commit เข้า git ด้วยไหม

ใช่ ตั้งใจให้เป็นแบบนั้น work item แต่ละตัวจะมีไฟล์ state เป็น JSON หนึ่งไฟล์ พร้อม audit
log แบบ append-only อยู่ใต้ `.jarvis/state/` และทั้งสองไฟล์ตั้งใจให้ commit ไปพร้อมกับ
`.claude/`, `.jarvis/` และ `docs/work/` เพราะ state แยกเก็บตาม work item แทนที่จะรวมอยู่
ในไฟล์เดียว คนสองคนที่ทำงานคนละ work item จะไม่มีทางชนกันบนบรรทัดเดียวกัน คุณไม่ควรแก้ไข
ไฟล์เหล่านี้ด้วยมือเด็ดขาด มีแค่ CLI (`node .jarvis/scripts/jarvis.js set|task|flags|...`)
เท่านั้นที่เขียนได้ และกฎ G1 ของ `guard.js` จะสกัดการแก้ไข `.jarvis/state/` โดยตรง

## bugfix กับ hotfix ต่างกันอย่างไร

ทั้งสองอย่างแก้ defect เหมือนกัน แต่ใช้กันคนละสถานการณ์:

| | Bugfix (`BUG`) | Hotfix (`HOT`) |
|---|---|---|
| ความเร่งด่วน | ไม่เร่งด่วน | เหตุขัดข้องบน production |
| เฟส | intake → investigation → plan → implement → test → review → **qa** → release | intake → investigation → implement → test → review → release → **postmortem** |
| เฟส QA | จำเป็น | ข้ามไปเลยทั้งหมด |
| Postmortem | ไม่มี | มี แต่ `deferrable: 3d` — ทำได้ภายใน 3 วันหลัง release |
| Reviewer ที่บล็อกได้ | ครบทั้งสี่ reviewer | เฉพาะ `security` และ `standards` |

hotfix แลกเฟส QA แบบเต็มและ postmortem ทันทีเพื่อความเร็ว แต่ยังคงบังคับให้มี review และ
ยังต้องเขียน postmortem อยู่ดี เพียงแต่ทำหลังจากแก้ปัญหาเสร็จแล้วภายใน 3 วัน ดูรายละเอียด
ได้ที่ `.jarvis/core/workflows/bugfix.yaml` และ `.jarvis/core/workflows/hotfix.yaml`

## spike คืออะไร และทำไมถึงไม่มีเฟส implementation

spike (`SPK`) คืองานวิจัยแบบตั้งกรอบเวลา (time-boxed) ที่ผลลัพธ์สุดท้ายคือการตัดสินใจ
ไม่ใช่การ merge โค้ด workflow ของมันมีแค่สองเฟสเท่านั้นคือ `intake` และ `investigation`
โดย `investigation` จะออกผลเป็น `spike-report.md` พร้อม ADR ฉบับร่าง แทนที่จะเป็น
`investigation.md` แบบปกติ ไม่มีเฟส `plan`, `implement`, `test`, `review`, `qa` หรือ
`release` เลย เพราะ spike ถูกออกแบบมาให้ไม่สร้าง production code ถ้าผลสรุปของ spike บอกว่า
ควรสร้างอะไรบางอย่าง สิ่งนั้นจะกลายเป็น work item แยกต่างหากที่สร้างด้วย `jarvis.js new`
ไม่ใช่การสานต่อจาก spike เดิม ดู [ความรู้เบื้องต้น](/docs/introduction) และ
`.jarvis/core/workflows/spike.yaml`

## กำหนดโมเดลแยกตาม agent เองได้ไหม

ได้ ผ่าน `models.overrides` ใน `jarvis.config.yaml`:

```yaml
models:
  default: inherit
  overrides:
    jarvis-gatekeeper: opus
    jarvis-architect: opus
    jarvis-review-security: opus
    jarvis-release: haiku
```

`default: inherit` หมายความว่า agent ที่ไม่มีการ override จะรันด้วยโมเดลเดียวกับที่เซสชัน
Claude Code ของคุณกำลังใช้อยู่ ส่วน agent ที่อยู่ใน `overrides` จะรันด้วยโมเดลที่ระบุไว้แทน
โดยตัวติดตั้ง (installer) จะใส่ค่านี้ลงใน frontmatter ของ agent นั้น ๆ ดู config schema
ที่เหลือได้ที่ [การตั้งค่า](/docs/configuration)

## การ upgrade จะแตะต้อง standards ของเราไหม

ไม่ `npx jarvis-framework upgrade` จะแทนที่เฉพาะไฟล์ที่เฟรมเวิร์กเป็นเจ้าของเท่านั้น ได้แก่
`.jarvis/core/`, `.jarvis/scripts/`, `.claude/agents/` และ `.claude/commands/` แล้วพิมพ์
รายการที่เปลี่ยนแปลงออกมา ส่วน `.jarvis/standards/`, `jarvis.config.yaml`,
`.jarvis/project/` และ `CLAUDE.md` เป็นของโปรเจกต์เอง จะไม่ถูกเขียนทับโดย `init` หรือ
`upgrade` เลย แม้ว่าค่าเริ่มต้นที่มาพร้อมเฟรมเวิร์กจะเปลี่ยนไปก็ตาม ดูรายละเอียดการแบ่ง
ความเป็นเจ้าของแบบเต็มได้ที่ [การใช้งานแบบทีม](/docs/team)
