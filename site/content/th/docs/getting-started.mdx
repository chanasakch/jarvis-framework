## สิ่งที่ต้องมี

เครื่องมือที่ต้องมีทุกกรณีมีสองตัว ที่เหลือจำเป็นเฉพาะเมื่อใช้มาตรฐาน Go + React ที่ให้มาในชุด

| สิ่งที่ต้องมี | Profile | หมายเหตุ |
|---|---|---|
| Node.js ≥18 | ต้องมีทุกกรณี | ใช้รัน `.jarvis/scripts` |
| git | ต้องมีทุกกรณี | ใช้ `user.name` บันทึกว่าใครสั่ง `approve`/`force` |
| Go | Go + React | `go version` |
| golangci-lint | Go + React | [ติดตั้ง](https://go.dev/dl/) |
| govulncheck | Go + React | `go install golang.org/x/vuln/cmd/govulncheck@latest` |
| Docker | Go + React | ใช้รัน integration test ที่ใช้ testcontainers |

`jarvis.js doctor` จะเช็กเครื่องมือทั้งหมดนี้กับ `PATH` ในเครื่องคุณ ดูหัวข้อ
[ตรวจสอบการตั้งค่า](#ตรวจสอบการตั้งค่า) ด้านล่าง

## ติดตั้ง

```bash
npx github:chanasakch/jarvis-framework init --name jarvis
cd .jarvis && npm install
```

`init` ไม่เขียนทับไฟล์ที่เป็นของคุณ รันซ้ำหลังอัปเกรดเฟรมเวิร์กได้ `.jarvis/standards/`,
`jarvis.config.yaml` และ `CLAUDE.md` จะยังอยู่เหมือนเดิม ส่วน `--name` ใช้ตั้ง prefix ของ slash command
และ agent ทุกตัว เช่น `--name ops` จะได้ `/ops`, `/ops-init` และ `ops-architect`

framework จะไม่เขียนทับไฟล์กลุ่มนี้

## ตรวจสอบการตั้งค่า

```bash
node .jarvis/scripts/jarvis.js doctor
```

```text
tools:    ✅ node  ✅ git  ❌ go  ❌ golangci-lint  ❌ govulncheck  ❌ docker
paths:    ✅ docs  ✅ adr  · web  · api  ✅ packages  ✅ error_registry  · migrations_mysql  · migrations_mongo  · openapi
registry: ✅ 7 codes
no problems
hint: go → https://go.dev/dl/
hint: golangci-lint → brew install golangci-lint
hint: govulncheck → go install golang.org/x/vuln/cmd/govulncheck@latest
hint: docker → needed for testcontainers integration tests
```

`·` หน้า path แปลว่ารีโปนี้ยังไม่มี path นั้น ซึ่งเป็นเรื่องปกติถ้ายังไม่ได้สร้าง `apps/web`/`apps/api`
ถ้าขาดเครื่องมือของ Go งานที่บล็อกจะมีแค่งานที่ต้องใช้เครื่องมือนั้น ขั้นต่อไปให้รัน `/jarvis-init` เพื่อสแกนรีโป
และเติมข้อมูลใน `.jarvis/project/context.md`

## Work item แรกของคุณ

<Steps>
<Step title="สแกนรีโป">
```text
/jarvis-init
```
เขียน `.jarvis/project/context.md` (stack, repo map, domain, pattern ที่ใช้อยู่,
glossary) จากโค้ดที่มีอยู่จริงในรีโป
</Step>
<Step title="เริ่ม work item">
```text
/jarvis Add OTP login for returning customers
```
orchestrator จะจัดประเภทงาน ถามคำถาม intake flag ไม่เกิน 5 ข้อในข้อความเดียว แล้วรัน phase ต่อไปเองตามลำดับ
ดูว่า work type แต่ละแบบมี phase อะไรบ้างได้ที่ [เวิร์กโฟลว์](/docs/workflows)
</Step>
<Step title="อ่าน status report">
ทุกรอบจะจบด้วย status report เสมอ ไม่ว่าผลจะออกมาอย่างไร
```text
── JARVIS ─────────────────────────────
Item:   FEAT-012 OTP login (feature)
Phase:  architecture → passed (attempt 1) ✅
Waiting: human approval
Next:   ! npm run -s jarvis -- approve FEAT-012 architecture
Warnings: none
───────────────────────────────────────
```
</Step>
<Step title="อนุมัติ phase">
`approve` เป็นคำสั่งที่คนต้องรันเอง `guard.js` จะบล็อกไม่ให้ Claude รันคำสั่งนี้ ให้รันคำสั่งตามที่
status report แสดงไว้
```text
! npm run -s jarvis -- approve FEAT-012 architecture
```
`!` ข้างหน้าคือการรันคำสั่งในเทอร์มินัลของคุณเอง ไม่ได้ให้ Claude รันแทน ดูว่ามีคำสั่งไหนอีกบ้างที่คนต้องรันเอง
และเพราะอะไรได้ที่ [เกต](/docs/gates)
</Step>
</Steps>

## ขั้นต่อไป

<Callout kind="tip">
เรียก `/jarvis-status` เมื่อไหร่ก็ได้เพื่อดู work item ที่ยังเปิดอยู่ทั้งหมดพร้อมคำเตือน ส่วน
`/jarvis-explain <ID>` จะบอกว่า work item นั้นติดอะไรอยู่ และต้องทำอะไรถึงจะไปต่อได้
</Callout>
