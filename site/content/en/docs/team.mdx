## Installing for a team

Every teammate runs the same install once per repo:

```bash
npx jarvis-framework init --name jarvis     # or --name ops, --name sdlc, …
cd .jarvis && npm install                   # one dependency: yaml
node .jarvis/scripts/jarvis.js doctor       # tools, paths, error registry
```

`--name` sets the prefix for slash commands and agents — `--name ops` gives `/ops`, `/ops-init` and
an `ops-architect` agent. Internal paths (`.jarvis/`, `jarvis.config.yaml`) always keep their own
names regardless of the prefix.

`init` **never overwrites a file your team owns.** Re-running it is safe: framework files are
refreshed, and your standards, `jarvis.config.yaml` and `CLAUDE.md` are left alone. After install,
restart Claude Code so it loads the new hooks, agents and commands, then run `/jarvis-init` to scan
the repo and write `.jarvis/project/context.md`.

Commit `.claude/`, `.jarvis/` and `docs/work/`, including `.jarvis/state/` — state is one small JSON
file plus an append-only audit log per work item, so two people working different items don't
conflict.

## The CI gate

The ready-made workflow (`project-templates/.github/workflows/jarvis.yml`) runs a `gate` job on
every PR into `main`, alongside separate `backend` and `frontend` check jobs that only run when
`apps/api/go.mod` or `apps/web/package.json` exist. After checkout and `npm install` in `.jarvis/`,
the `gate` job's enforcement steps are:

```bash
node .jarvis/scripts/jarvis.js ci --base origin/main
node .jarvis/scripts/audit.js
node --test ".jarvis/scripts/test/*.test.js"
```

`jarvis.js ci` reads the current branch name, extracts a work item ID from it (matching
`[A-Z]+-\d{3}`), and fails when any of the following is true:

- That work item has a phase whose status isn't `approved`, `passed`, `forced`, or `skipped`.
- `lint` (run with `--changed`) finds a `critical` or `major` violation.
- `packages/errors/registry.yaml` fails to parse, is missing a required field (`code`, `public`,
  `http`, `level`, `description`) on any entry, or has a duplicate `code`.

A GitLab equivalent ships at `project-templates/ci/gitlab-ci.example.yml`.

## CODEOWNERS

`project-templates/.github/CODEOWNERS` routes review to whichever group owns the thing being
changed, so a standards relaxation or a framework edit doesn't slip through on an unrelated
approval:

| Path | Reviewer | Why |
|---|---|---|
| `.jarvis/standards/` | tech leads | Relaxing a rule needs sign-off, not just any approval |
| `.jarvis/core/`, `.jarvis/scripts/`, `.claude/agents/`, `.claude/commands/`, `.claude/settings.json` | tech leads | Framework-owned; normally replaced by `upgrade`, not hand-edited |
| `packages/errors/registry.yaml` | tech leads + frontend | A public error key change is a breaking API change for every client |
| `jarvis.config.yaml` | tech leads | Controls who may weaken a gate |
| `docs/architecture/query-index-matrix.md` | tech leads + DBA | Index evidence backing the database standard |

The template ships placeholder team names (`@your-org/tech-leads`, `@your-org/frontend`,
`@your-org/dba`) — replace them with real teams before turning on branch protection.

## Upgrading

```bash
npx jarvis-framework upgrade
node .jarvis/scripts/audit.js                 # framework is internally consistent
node --test ".jarvis/scripts/test/*.test.js"  # scripts still behave
```

`upgrade` walks every file the framework ships, and for each one either writes it (new), replaces it
(changed), or leaves it alone (identical) — then writes the new `.jarvis/VERSION`. It only ever
touches framework-owned paths: `.jarvis/core/`, `.jarvis/scripts/`, `.claude/agents/`,
`.claude/commands/`, `.claude/settings.json`. It prints a summary of what was added, updated and left
unchanged.

Project-owned files are never touched by `upgrade`: `jarvis.config.yaml`, `CLAUDE.md`,
`.jarvis/standards/**`, `.jarvis/project/**`, and `packages/errors/registry.yaml`.

If an older version shipped an agent or command this version no longer ships, `upgrade` reports it
under "not shipped by this version" instead of deleting it — your team may have built on it, so the
decision to remove it is yours. Restart Claude Code afterwards so it picks up the change.

## Proposing a standards change

Standards live in your repo so your team can change them without touching the framework:

1. Open a PR against the file under `.jarvis/standards/`.
2. If the rule is machine-checkable, update `lint-rules.yaml` in the same PR.
3. **Relaxing or removing a rule additionally needs an ADR** in `docs/adr/`, naming the rule ID, the
   reason, the scope, and when it expires.
4. `CODEOWNERS` sends the PR to the group above that owns `.jarvis/standards/`.

See [Standards](/docs/standards) for the full rule-ID reference and the one-off exception mechanism
(`jarvis-ignore` plus an accepted ADR) for when a single line needs to deviate without changing the
rule itself.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `G1 BLOCKED` editing `.jarvis/core` or `.claude` | Those paths are framework-owned | Developing the framework itself? Start Claude Code with `JARVIS_DEV=1` |
| Commands or agents missing after upgrade | Claude Code reads them at session start | Restart Claude Code |
| CI fails with no listed phase issue | `lint` or the error registry check failed | Run `jarvis.js lint --changed` locally to see the finding |
