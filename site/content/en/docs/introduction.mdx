## What Jarvis is

Jarvis is an AI-driven SDLC framework that runs on Claude Code. It routes work to specialist
subagents and checks every output against your team's standards through a three-layer gate:
a deterministic script, a gatekeeper agent, then human approval on the phases that need it.
No phase moves forward until it meets its Definition of Done.

<Callout kind="note" title="Built for one stack, not locked to it">
The shipped standards target a monorepo with a React + TypeScript frontend and a Go backend,
using MySQL and MongoDB. The mechanism (rules with IDs, checked by a script and an agent)
works for any stack. Only the `.jarvis/standards/*.md` files are stack-specific. They're
project-owned, so your team edits them directly.
</Callout>

## Why it exists

Left to itself, an AI coding agent writes plausible code that ignores your team's standards:
a `JOIN` where you agreed never to use one, a query with no supporting index, a raw database
error returned to the browser, an acceptance criterion with no test. You won't catch these by
reading the code once. They surface in an incident, or in the same review comments written
over and over.

Jarvis turns every standard into a rule with an ID (`.jarvis/standards/*.md`), and every rule
into a check that a script or an agent runs before the work can move on. Ten design
principles hold this together:

1. **Orchestrator = slash command.** `/jarvis` runs in your main session. Subagents cannot
   spawn subagents, so every handoff goes through it.
2. **File-based handoff.** Agents exchange file paths, never pasted content. Every artifact
   lives in `docs/work/<ID>-<slug>/`.
3. **Three-layer gates.** A deterministic script, then a gatekeeper agent with evidence, then
   a human for the phases that need one. See [Gates](/docs/gates).
4. **Hooks enforce hard rules.** `guard.js` blocks anything that must never happen before the
   tool call runs, instead of catching it afterwards. Examples: editing a framework file,
   running a human-only command, touching a migration with no declared schema change.
5. **Traceability by ID.** `FR → US → AC → TC → code → release`. Every requirement, story,
   criterion, task and finding carries an ID.
6. **Configuration over code.** Workflows, gates, commands and thresholds live in
   `jarvis.config.yaml` and `.jarvis/core/workflows/*.yaml`, not hardcoded logic.
7. **Framework-owned vs. project-owned.** `.jarvis/core`, `.jarvis/scripts`, `.claude/agents`
   and `.claude/commands` are replaced on upgrade. `.jarvis/standards`, `jarvis.config.yaml`
   and `CLAUDE.md` never are.
8. **Every exception needs an ADR.** A standard can be relaxed for a specific case, but the
   exception has to be written down and reference the rule ID.
9. **Strict by default.** You can force past a failed gate, but only a human can do it. It
   requires a reason, is audited, and creates a follow-up item for whatever is unresolved.
10. **Token discipline.** Artifacts are short and in English. An agent reads only the
    standards its phase needs.

## When not to use it

Jarvis adds overhead: intake questions, gated phases, and human approval on some of them.
That cost pays off on work that outlives a single session, such as a feature, a fix that
needs a proper root cause, or anything that touches production. It's the wrong tool for a
one-line typo fix, a throwaway experiment, or a change with no code. For research where the
deliverable is a decision rather than a merge, use the `spike` work type. It ends after
investigation, with no implementation phase.
