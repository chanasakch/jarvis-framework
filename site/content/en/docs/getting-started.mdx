## Requirements

Two tools are always required. The rest matter only if you use the shipped Go + React
standards.

| Requirement | Profile | Notes |
|---|---|---|
| Node.js ≥18 | Always | Runs `.jarvis/scripts` |
| git | Always | Records `approve`/`force` actors via `user.name` |
| Go | Go + React | `go version` |
| golangci-lint | Go + React | [Install](https://go.dev/dl/) |
| govulncheck | Go + React | `go install golang.org/x/vuln/cmd/govulncheck@latest` |
| Docker | Go + React | Needed for testcontainers integration tests |

`jarvis.js doctor` checks all of these against your `PATH`. See [Verify the
setup](#verify-the-setup) below.

## Install

```bash
npx github:chanasakch/jarvis-framework init --name jarvis
cd .jarvis && npm install
```

`init` never overwrites a file you already own. If you run it again after upgrading the
framework, your `.jarvis/standards/`, `jarvis.config.yaml` and `CLAUDE.md` are left
untouched. `--name` sets the prefix for every slash command and agent. For example,
`--name ops` gives you `/ops`, `/ops-init` and `ops-architect` instead.

## Verify the setup

```bash
node .jarvis/scripts/jarvis.js doctor
```

```text
tools:    ✅ node  ✅ git  ❌ go  ❌ golangci-lint  ❌ govulncheck  ❌ docker
paths:    ✅ docs  ✅ adr  · web  · api  ✅ packages  ✅ error_registry  · migrations_mysql  · migrations_mongo  · openapi
registry: ✅ 7 codes
no problems
hint: go → https://go.dev/dl/
hint: golangci-lint → brew install golangci-lint
hint: govulncheck → go install golang.org/x/vuln/cmd/govulncheck@latest
hint: docker → needed for testcontainers integration tests
```

A `·` next to a path means it doesn't exist in this repo yet. That's expected before
`apps/web`/`apps/api` exist. Missing Go tooling only blocks work that needs it. Next, run
`/jarvis-init` to scan the repo and fill in `.jarvis/project/context.md`.

## Your first work item

<Steps>
<Step title="Scan the repo">
```text
/jarvis-init
```
Writes `.jarvis/project/context.md` (stack, repo map, domains, existing patterns,
glossary) from what's in your codebase.
</Step>
<Step title="Start a work item">
```text
/jarvis Add OTP login for returning customers
```
The orchestrator classifies the work type and asks up to five intake flag questions in one
message. Then it runs the phase sequence on its own. See [Workflows](/docs/workflows) for
the phases each work type runs.
</Step>
<Step title="Read the status report">
Every turn ends with a status report, whatever happened:
```text
── JARVIS ─────────────────────────────
Item:   FEAT-012 OTP login (feature)
Phase:  architecture → passed (attempt 1) ✅
Waiting: human approval
Next:   ! npm run -s jarvis -- approve FEAT-012 architecture
Warnings: none
───────────────────────────────────────
```
</Step>
<Step title="Approve a phase">
`approve` is human-only: `guard.js` blocks Claude from running it. Run the command the
status report gave you:
```text
! npm run -s jarvis -- approve FEAT-012 architecture
```
The `!` runs it directly in your terminal rather than asking Claude to. See
[Gates](/docs/gates) for what else is human-only and why.
</Step>
</Steps>
